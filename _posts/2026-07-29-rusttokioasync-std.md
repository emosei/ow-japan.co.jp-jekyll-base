## 「同じコードなのに速度が変わる」という現場の違和感

Rustで非同期処理を書くとき、多くのプロジェクトはtokioを選びます。実績も多く、ドキュメントも充実しているからです。ただ、既存のasync-stdベースのコードを引き継いだり、特定の環境で動かしたりすると、「ランタイムを切り替えるだけで同じロジックのスループットが2〜3倍変わる」という経験をすることがあります。

これは単なる実装の良し悪しではなく、ランタイムの設計思想とあなたのシステムの特性がどう噛み合うか、という問題です。その見極め方を整理してみます。

## 検証の前に押さえておくべき設計の違い

tokioとasync-stdは、どちらも「async/awaitを動かす仕組み」ですが、内部の戦略が異なります。

**tokio の特徴**
- マルチスレッドランタイムが標準。OSスレッドプールを複数持つ
- ワークスティーリング（タスクの動的な負荷分散）を積極的に行う
- スケジューリングのオーバーヘッドが大きい代わり、スループット重視
- 大量の並行タスク、I/O待機が多い環境で有利

**async-std の特徴**
- シングルスレッドランタイムが標準（マルチスレッド版も存在）
- タスク間のコンテキストスイッチが少ない
- メモリ使用量が抑えめ、レイテンシ予測が立てやすい
- CPU使用率が限定的な環境、またはI/O待機が少ない環境で相対的に有利

この違いが、同じコードでも環境によって性能差を生むのです。

## 実際の検証構成と測定方法

違いを確かめるため、簡単な負荷テストを設計します。

**テスト環境の想定**
- ローカルループバックでのHTTP リクエスト・レスポンス
- 並行数：100、1000、5000のバリエーション
- レスポンス時間：ほぼ0ms（ネットワーク遅延なし）
- テスト期間：各パターン30秒間

このシンプルな構成で、ランタイムの「スケジューリング効率」をダイレクトに測定できます。

**tokioでの実装例**
```rust
use tokio::net::TcpListener;
use std::sync::Arc;
use std::sync::atomic::{AtomicU64, Ordering};

#[tokio::main]
async fn main() {
    let listener = TcpListener::bind("127.0.0.1:8080").await.unwrap();
    let counter = Arc::new(AtomicU64::new(0));

    loop {
        let (socket, _) = listener.accept().await.unwrap();
        let counter = counter.clone();
        tokio::spawn(async move {
            // 最小限のレスポンス処理
            let _ = socket.try_write(b"HTTP/1.1 200 OK\r\n\r\n");
            counter.fetch_add(1, Ordering::Relaxed);
        });
    }
}
```

**async-std での実装例**
```rust
use async_std::net::TcpListener;
use std::sync::Arc;
use std::sync::atomic::{AtomicU64, Ordering};

#[async_std::main]
async fn main() {
    let listener = TcpListener::bind("127.0.0.1:8080").await.unwrap();
    let counter = Arc::new(AtomicU64::new(0));

    loop {
        let (socket, _) = listener.accept().await.unwrap();
        let counter = counter.clone();
        async_std::task::spawn(async move {
            // 最小限のレスポンス処理
            let _ = socket.write_all(b"HTTP/1.1 200 OK\r\n\r\n").await;
            counter.fetch_add(1, Ordering::Relaxed);
        });
    }
}
```

コードはほぼ同じです。違いは `#[tokio::main]` か `#[async_std::main]` かだけ。ここで測定すると、実環境では大きな差が出ます。

## 実測から見えてくる選択基準

現場での検証結果をまとめると、以下のパターンが見えてきます。

### 1. I/O待機が支配的な環境（Web API、データベースアクセス）
- **tokioが有利**：複数スレッドでのワークスティーリングにより、あるタスクがI/O待機中でも他のタスクが進行しやすい
- **目安**：5000以上の並行接続、平均応答時間が数100ms以上

### 2. CPU負荷が高い環境（画像処理、データ変換）
- **async-stdが有利**：スレッド数が少ないため、コンテキストスイッチのオーバーヘッドが低い
- **目安**：CPU時間が大半を占める処理、並行数が100以下

### 3. メモリに制約がある環境（エッジデバイス、組み込み）
- **async-stdが有利**：スレッドプールのメモリ消費が少ない
- **目安**：ヒープサイズが限定的（数100MB以下）

### 4. レイテンシ予測が重要な環境（リアルタイム処理）
- **async-stdが有利**：GCやスケジューリング遅延が予測しやすい
- **目安**：p99レイテンシが明確に定義されている案件

## 実務投入前に確認すべきポイント

単なる性能測定だけでは判断できない、運用面での注意があります。

**ランタイム切り替えのコスト**
- 既存のtokio依存ライブラリ（hyper、sqlxなど）がasync-stdで動くか確認が必要
- 多くのエコシステムはtokio中心のため、async-stdでは選択肢が限定される
- 切り替えは「性能が良い」だけでは正当化しにくい

**本番環境での挙動**
- ローカルループバックでの測定と、ネットワーク越しの実測は別
- クラウド環境（AWS、GCP）のI/O特性によって、相対的な優位性が変わることがある
- 長時間運用時のメモリリーク、スケジューラーの退化がないか確認

**チーム側の判断**
- tokioはドキュメント、書籍、ブログ記事が豊富。障害時の問題解決が容易
- async-stdはコミュニティが小さく、困ったときの情報が限定的
- 新規プロジェクトなら「なぜasync-stdなのか」を明確にできるか

## 現実的な選択フロー

迷ったときの判断順序です。

1. **既存の制約を確認**：使用予定のライブラリがtokio依存か
2. **負荷パターンを測定**：I/O待機時間の比率を計測
3. **リソース制約を確認**：メモリ、CPU、スレッド数の上限
4. **プロトタイプで検証**：実装予定の負荷パターンで両者を試す
5. **運用性を天秤にかける**：性能差とドキュメント・サポートのトレードオフを判定

多くの場合、tokioが「無難な選択」です。ただ、明確な制約条件（メモリが極端に少ない、I/O待機がほぼない）があれば、async-stdの検討は十分に価値があります。

## まとめ：測定なしの判断は危ない

「tokioが標準だから」という理由だけで選ぶのも、「性能が良いから」という理由だけで切り替えるのも、どちらも実務では失敗のもとです。

あなたのシステムがどんな負荷パターンを持つのか、メモリやスレッドにどんな制約があるのか、そしてチームがどの程度の技術サポートを期待できるのか。そうした前提を整理してから、初めて選択が意味を持ちます。

現場では「速い」と「安定」と「保守しやすい」のバランスが、性能値そのものより重要になることが多いです。
