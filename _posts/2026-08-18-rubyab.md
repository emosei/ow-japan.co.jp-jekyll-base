## 複数テスト並行時に検証負荷が急増する理由

アジャイル開発でスプリントサイクルが短くなるほど、複数の機能フラグ（feature flag）が同時に本番環境で動作する状況が増えます。特にA/Bテストを複数並行させている場合、各テストの制御ロジックが独立していると、デプロイ前の検証項目が指数関数的に増えてしまいます。

現場ではこういう判断が起きやすいです。「今週のスプリントではAテストとBテストを同時実行する。それぞれ異なるユーザーセグメントを対象にしているから干渉しないはず」と判断して進めると、本番デプロイの直前に「でも万が一セグメント判定がズレたら両方のテストが同じユーザーに当たるケースがあり得るな」という懸念が浮上します。結果として、テスト環境での再検証が増え、スプリント終盤に時間が吸収されていく。

問題の根底は、機能フラグの**有効化・無効化ロジック**と**テスト対象ユーザーの選別ロジック**が、各テストごとに分散しているからです。これらが増えるほど、組み合わせ爆発が起きやすくなります。

## 機能フラグ管理の一元化が検証コストを下げる

複数のA/Bテストを安全に並行させるには、機能フラグの定義と評価を一元化する必要があります。具体的には、以下のような構造にします。

```ruby
# config/feature_flags.yml
features:
  checkout_redesign:
    enabled: true
    test_type: "ab_test"
    segment_rule: "user_id_modulo"
    segment_params:
      modulo: 100
      target_range: [0, 49]  # 0〜49のユーザーがテスト対象
    rollout_percentage: 50
    
  payment_gateway_v2:
    enabled: true
    test_type: "ab_test"
    segment_rule: "region_based"
    segment_params:
      regions: ["JP-13", "JP-14"]  # 特定地域のみ
    rollout_percentage: 25
    
  recommendation_engine:
    enabled: false
    test_type: "canary"
    segment_rule: "user_tier"
    segment_params:
      tiers: ["premium"]
    rollout_percentage: 10
```

このYAMLファイルを単一の真実の源（Single Source of Truth）として、全ての機能フラグ評価がここを参照するようにします。

```ruby
# app/services/feature_flag_evaluator.rb
class FeatureFlagEvaluator
  def self.enabled?(flag_name, user)
    config = load_config[flag_name.to_s]
    return false unless config && config["enabled"]
    
    # ロールアウトパーセンテージの確認
    return false unless within_rollout?(flag_name, user, config["rollout_percentage"])
    
    # セグメント判定ロジック
    evaluate_segment(user, config["segment_rule"], config["segment_params"])
  end
  
  private
  
  def self.within_rollout?(flag_name, user, percentage)
    hash_value = Digest::MD5.hexdigest("#{flag_name}:#{user.id}").to_i(16)
    (hash_value % 100) < percentage
  end
  
  def self.evaluate_segment(user, rule_type, params)
    case rule_type
    when "user_id_modulo"
      modulo = params["modulo"]
      target_range = params["target_range"]
      remainder = user.id % modulo
      target_range[0] <= remainder && remainder <= target_range[1]
    when "region_based"
      params["regions"].include?(user.region_code)
    when "user_tier"
      params["tiers"].include?(user.tier)
    else
      false
    end
  end
  
  def self.load_config
    @config ||= YAML.load_file(Rails.root.join("config/feature_flags.yml"))
  end
end
```

この方式の利点は、各機能フラグの有効化・セグメント判定・ロールアウト戦略が一箇所に集約されることです。結果として、本番デプロイ前に「これらのテストが同じユーザーに当たるか」「ロールアウトパーセンテージの合計が100%を超えていないか」といった検証が、設定ファイルを眺めるだけで可能になります。

## スプリント内での検証チェックリスト化

複数テスト並行時の検証漏れを防ぐには、チェックリストを明示的に作ることが有効です。

```ruby
# spec/services/feature_flag_validator_spec.rb
RSpec.describe FeatureFlagValidator do
  describe "複数テストの並行実行検証" do
    it "同じユーザーセグメントが複数のテストに割り当たっていないこと" do
      user = User.create(id: 12345, region_code: "JP-13", tier: "standard")
      
      # このスプリントで有効なテスト一覧
      active_tests = [:checkout_redesign, :payment_gateway_v2]
      
      assigned_tests = active_tests.select do |flag|
        FeatureFlagEvaluator.enabled?(flag, user)
      end
      
      # 同時に複数のA/Bテスト対象になってないか確認
      expect(assigned_tests.length).to be <= 1
    end
    
    it "ロールアウトパーセンテージの合計が妥当な範囲内であること" do
      config = YAML.load_file(Rails.root.join("config/feature_flags.yml"))
      active_rollouts = config.select { |_, v| v["enabled"] && v["test_type"] == "ab_test" }
      total_percentage = active_rollouts.sum { |_, v| v["rollout_percentage"] }
      
      # 通常は50%以下に抑える（複数テストの干渉を避けるため）
      expect(total_percentage).to be <= 50
    end
    
    it "セグメント定義が矛盾していないこと" do
      validator = FeatureFlagValidator.new
      conflicts = validator.detect_segment_conflicts
      expect(conflicts).to be_empty
    end
  end
end
```

このテストスイートをスプリント終盤のマージリクエスト時に実行することで、設定ファイルの矛盾を自動検出できます。

## 運用時にハマりやすい落とし穴

### 1. ハッシュ値の一貫性

ロールアウトの判定に `user.id % 100` のような単純な剰余演算を使うと、ユーザーIDの分布が偏っている場合にテスト対象が不均等になります。上記の例では `Digest::MD5` でハッシュ化することで、より均等な分散を実現しています。

### 2. 設定ファイルの更新反映遅延

YAMLファイルをメモリにキャッシュしている場合、本番環境での設定変更が即座に反映されません。以下のように、定期的にリロードするか、外部キャッシュ（Redis等）を使うことをお勧めします。

```ruby
# config/initializers/feature_flags.rb
class FeatureFlagCache
  CACHE_KEY = "feature_flags_config"
  CACHE_TTL = 5.minutes
  
  def self.get
    Rails.cache.fetch(CACHE_KEY, expires_in: CACHE_TTL) do
      YAML.load_file(Rails.root.join("config/feature_flags.yml"))
    end
  end
  
  def self.refresh
    Rails.cache.delete(CACHE_KEY)
  end
end
```

### 3. 無効化テストの検証漏れ

機能フラグを無効化する際、実際に無効化されたコード経路が本番で動作しているか確認しないまま進めると、後々バグが顕在化します。スプリント終了時に「このフラグを無効化したら、フォールバック側が正常に動作しているか」を必ず検証してください。

## 小規模チームでの段階的導入

大規模なFeature Flag管理サービス（LaunchDarkly等）の導入は初期コストが高いため、小規模チームなら上記のようなシンプルな実装から始めるのが現実的です。

**段階1（1スプリント目）**
- YAML設定ファイルと基本的な評価ロジックを実装
- 既存の機能フラグをここに移行

**段階2（3スプリント目）**
- 検証テストスイートを追加
- CI/CDパイプラインに組み込み

**段階3（5スプリント目以降）**
- 必要に応じて外部キャッシュを導入
- ダッシュボード（管理画面）の実装を検討

このペースなら、チームの負担を最小化しつつ、検証コストを段階的に削減できます。

## 判断のポイント

複数A/Bテストを並行させるとき、「セグメント判定が正確か」「ロールアウト戦略が競合していないか」という2点に絞って検証する習慣をつけることが大切です。機能フラグの一元化は、この検証を効率的にする手段に過ぎません。

スプリント内の検証コスト削減は、短期的には「テストに落ちる確率を下げる」ことですが、中期的には「チーム全体がフラグ管理の複雑さに習熟する」ことにつながります。その先に、より多くのテストを並行させる余裕が生まれます。
