## 問題の背景──開発環境では動くのに本番で落ちる

Railsアプリケーションを運用していると、キャッシュストアを切り替える場面があります。開発環境ではメモリ（`:memory_store`）で十分でも、本番環境ではRedisやMemcachedへの移行を検討する。その判断自体は正しいのですが、実装の細部でシリアライゼーション（オブジェクトの直列化）の仕様がズレていると、本番環境特有の障害が発生しやすいです。

現場では「開発環境では問題なく動いたのに、本番デプロイ直後にキャッシュヒット時だけエラーが出る」という報告が上がります。デバッグ時間が限られているなか、ストアの切り替えが原因だと気づくまでに相応の手戻りが発生することが多いです。

本記事では、実際に複数のキャッシュストアを試して、シリアライゼーション周りで何が変わるのか、どこで障害が潜みやすいのかを整理します。

## 検証の前提と構成

### 検証の目的

異なるキャッシュストア間で、オブジェクトの保存・復元時に挙動がどう変わるか、実装上どこに注意が必要かを明らかにする。

### テスト環境

- Ruby 3.1系
- Rails 7.0系
- 比較対象: `:memory_store`、Redis（redis-rb）、Memcached（dalli gem）
- テスト対象: 単純なHash、ActiveRecord オブジェクト、カスタムクラスのインスタンス

### 比較の観点

1. デフォルトのシリアライザ動作
2. カスタムオブジェクトの復元時の挙動
3. クラス定義の変更がキャッシュに与える影響
4. 日時、タイムゾーン情報の扱い

## メモリストアとRedis・Memcachedのシリアライゼーション差

### メモリストアの「甘さ」

`:memory_store`はRailsプロセスのメモリ上に直接Rubyオブジェクトを保持します。つまり、シリアライズされず、Rubyの参照として存在しています。

```ruby
# config/environments/development.rb
config.cache_store = :memory_store, { size: 32.megabytes }
```

この場合、キャッシュに保存したオブジェクトは「そのまま」取り出されます。クラス定義が同じプロセス内にあれば、インスタンス変数の型チェックも緩くなります。

### Redis・Memcachedの「厳密さ」

一方、RedisやMemcachedはネットワーク越しのキーバリューストアです。保存時にシリアライズし、取得時にデシリアライズします。デフォルトではRailsは `Marshal.dump` / `Marshal.load` を使います。

```ruby
# config/environments/production.rb
config.cache_store = :redis_cache_store, { url: ENV['REDIS_URL'] }
```

Marshalはバイナリフォーマットで、クラスの定義が取得時に存在しなければ `ArgumentError` や `TypeError` が発生します。

## 実装上の落とし穴

### 1. クラス定義の削除や移動

開発中にモデルやクラスをリファクタリングする場合、既にキャッシュに入っているオブジェクトのクラスが見つからなくなる可能性があります。

```ruby
# 以前のバージョン: app/models/user_cache.rb に UserCache クラスがあった
class UserCache
  attr_accessor :user_id, :name
end

# リファクタリング後: UserCache クラスを削除し、Userモデルに統合
# すると、キャッシュから復元しようとして...
# ArgumentError: undefined class/module UserCache
```

メモリストアではプロセスが再起動されれば消えますが、Redisのキャッシュは永続化される可能性があり、デプロイ直後に本番環境で発火します。

### 2. インスタンス変数の型の暗黙的な変更

```ruby
class OrderSummary
  attr_accessor :total_price, :item_count, :created_at
  
  def initialize(price, count)
    @total_price = price      # Float
    @item_count = count       # Integer
    @created_at = Time.current
  end
end
```

後で実装を変更し、`total_price` を `BigDecimal` に変えたとします。

```ruby
class OrderSummary
  attr_accessor :total_price, :item_count, :created_at
  
  def initialize(price, count)
    @total_price = BigDecimal(price)  # 変更
    @item_count = count
    @created_at = Time.current
  end
end
```

Redisから復元されたオブジェクトは古い型のままです。その後の計算で `@total_price + something` を実行すると、型不一致エラーが起きます。メモリストアではプロセス再起動で新しいクラス定義が読み込まれるため、この問題が顕在化しません。

### 3. タイムゾーン情報の喪失

Marshalで `Time` オブジェクトをシリアライズすると、タイムゾーン情報が失われることがあります。特に、ActiveSupport の `TimeWithZone` を使っている場合に顕著です。

```ruby
# キャッシュに保存
time_with_zone = Time.zone.now  # => 2024-12-15 10:30:00 +0900

Rails.cache.write('cached_time', time_with_zone)

# 後で復元
retrieved = Rails.cache.read('cached_time')
# retrieved は Time オブジェクト（TimeWithZone ではない）になっている可能性
```

開発環境ではタイムゾーン設定が同じため問題が出ませんが、本番環境でタイムゾーン設定が異なるコンテナで復元されると、時刻がズレます。

## 実装時の対策

### シリアライザを明示的に指定

Rails 7.1以降では、キャッシュストアごとにシリアライザを指定できます。

```ruby
# config/environments/production.rb
config.cache_store = :redis_cache_store,
  { url: ENV['REDIS_URL'] },
  { serializer: :json }  # または :message_pack など
```

JSONシリアライザを使えば、クラス定義に依存しません。ただし、保存可能な型が限定されます（Hash、Array、String、Number、Boolean、nil）。

### キャッシュキーにバージョン番号を含める

```ruby
def cache_key_for_order(order_id)
  # キャッシュスキーマのバージョンを含める
  "order:v2:#{order_id}:#{order.updated_at.to_i}"
end

Rails.cache.fetch(cache_key_for_order(123)) do
  # キャッシュミス時の処理
end
```

クラス定義が変わったら、キャッシュキーのバージョンを上げます。これにより、古いキャッシュは自動的に無視されます。

### 型チェック・変換を明示的に行う

キャッシュから復元したオブジェクトに対して、期待する型であることを確認します。

```ruby
cached_data = Rails.cache.read('order_summary')

if cached_data.is_a?(OrderSummary)
  # 使用
else
  # キャッシュミス扱いで再生成
  cached_data = OrderSummary.new(...)
end
```

## 本番投入前の確認チェック

実装が完了したら、以下を確認してください。

1. **キャッシュストアの切り替えテスト**  
   開発環境でメモリストア、ステージング環境でRedis/Memcachedを使い、同じテストケースを実行する。

2. **クラス定義の変更シナリオ**  
   キャッシュに古いオブジェクトが入った状態で、クラス定義を変更してアプリを起動し、復元時の挙動を確認する。

3. **デプロイ後のキャッシュフラッシュ戦略**  
   本番環境でキャッシュストアを初めて切り替える場合は、デプロイ直後に `Rails.cache.clear` を実行するか、キャッシュキーのバージョンを上げるかのいずれかを決めておく。

4. **監視・ログ**  
   キャッシュの復元失敗時に例外を捕捉し、ログに記録する仕組みを用意する。

```ruby
def safe_cache_read(key)
  Rails.cache.read(key)
rescue => e
  Rails.logger.error("Cache read error for #{key}: #{e.message}")
  nil
end
```

## どんな案件で採用しやすいか

この検証内容は、特に以下のような案件で重要になります。

- **既存のRailsアプリをスケールさせる場合**  
  開発環境で動いていたキャッシュ戦略を、本番環境で別のストアに切り替えるとき。

- **複数のアプリケーションサーバーを立てる場合**  
  メモリストアから共有キャッシュストア（Redis等）への移行が必須。

- **長期運用のレガシーアプリ**  
  クラス定義の変更が頻繁に起き、キャッシュの互換性が問題になりやすい。

- **マイクロサービス化を検討している場合**  
  サービス間でキャッシュを共有する際、シリアライゼーション仕様の統一が重要。

逆に、キャッシュ戦略が単純で、クラス定義の変更が少ないアプリケーションであれば、この検証の優先度は下がります。

## まとめ

Railsのキャッシュストアを切り替えるのは、一見すると設定ファイルを変更するだけの簡単な作業に見えます。しかし、シリアライゼーション仕様の違いが、本番環境で予期しない障害を引き起こします。

開発環境と本番環境で同じストアを使うか、明示的にシリアライザを指定し、キャッシュキーにバージョンを含める。こうした実装上の工夫が、運用時の手戻りを減らします。
