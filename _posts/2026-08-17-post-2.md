## なぜメタデータ更新の失敗が認証全体を止めるのか

フェデレーション認証（SAML、OpenID Connect等）を採用している環境では、IdP（認証プロバイダ）が公開するメタデータを定期的に取得・更新する必要があります。メタデータには、署名用の公開鍵、エンドポイントURL、対応しているプロトコルバージョンなどが含まれています。

このメタデータ更新が失敗したときの動作が曖昧だと、本番環境で認証が全体停止する事態が起こります。

実務では、以下のようなシナリオが現実に発生します：

- IdPのメタデータエンドポイントが一時的にダウンしている
- ネットワーク遅延でタイムアウトが発生している
- IdPの証明書が更新され、署名検証に失敗している
- 古いメタデータでユーザーが認証を試みている

この局面で、アプリケーション側の動作が「更新失敗時は新しいメタデータを使わない」と「更新失敗時は古いメタデータをそのまま使い続ける」のどちらなのかが明確でないと、障害対応が混乱します。さらに、その判断がミドルウェアレベルで行われている場合、アプリケーション層では気づきにくくなります。

## 検証の目的と構成

実装の現場では、フェデレーション認証ライブラリやミドルウェアの設定ドキュメントに「メタデータ更新失敗時の動作」が明記されていないことが多いです。デフォルト動作に頼ると、本番環境で予期しない停止が起きます。

この検証では、以下を確認します：

- **メタデータ更新失敗時のデフォルト動作**：更新を再試行するのか、古いメタデータで継続するのか、エラーを返すのか
- **キャッシュの有効期限と更新タイミング**：メタデータがどの程度の期間保持され、どのタイミングで更新されるのか
- **署名検証失敗時の挙動**：古いメタデータで署名検証に失敗した場合、メタデータを強制更新するのか、認証を拒否するのか
- **フォールバック戦略の実装可能性**：複数のメタデータソース、オフライン用の固定メタデータ、更新失敗時の明示的な処理

## 一般的なライブラリの動作パターン

SAML2.0実装の主要ライブラリを調べると、メタデータ更新失敗時の動作は大きく3つに分かれます。

**パターンA：更新失敗時は古いメタデータで継続**

このパターンでは、メタデータ更新に失敗しても、メモリやキャッシュに保持されている古いメタデータを使い続けます。短期的な一時障害には強いですが、IdPが証明書をローテーションした場合、署名検証エラーが発生し始めます。

```
更新リクエスト → タイムアウト/エラー → ログ出力 → 古いメタデータで認証継続
```

**パターンB：更新失敗時は認証を拒否**

このパターンでは、メタデータ更新に失敗すると、新しい認証リクエストを拒否します。安全側に倒した設計ですが、IdPの一時的なダウンで全体が停止してしまいます。

```
更新リクエスト → タイムアウト/エラー → 認証リクエスト受け取り → 403/500エラー
```

**パターンC：複数の戦略を組み合わせる**

キャッシュの有効期限内なら古いメタデータを使い、有効期限切れで更新に失敗した場合は再試行、再試行も失敗したら明示的にエラーを返す、という段階的な対応です。

実装の詳細はライブラリによって異なります。

## 実装検証：Ruby on Railsでの具体例

Rails環境でSAML認証を実装する場合、`ruby-saml`ライブラリが広く使われています。このライブラリのメタデータ更新動作を確認してみます。

```ruby
# Gemfile
gem 'ruby-saml'

# config/initializers/saml_auth.rb
OneLogin::RubySaml::Metadata.settings = {
  :idp_metadata_parser_enabled => true,
  :idp_sso_service_url => "https://idp.example.com/metadata",
  :cache_duration => 3600  # 1時間
}
```

デフォルトでは、メタデータは初回アクセス時に取得され、`cache_duration`で指定された期間メモリに保持されます。この期間内は、IdPへのリクエストは発生しません。

問題は、キャッシュ有効期限が切れたときの動作です。

```ruby
# メタデータ更新時の実装例（ruby-samlの内部動作を簡略化）
def fetch_metadata(url)
  response = Net::HTTP.get_response(URI(url))
  
  if response.code == '200'
    parse_metadata(response.body)
  else
    # ここで何もしないと、古いメタデータが使われ続ける
    Rails.logger.warn("Metadata fetch failed: #{response.code}")
    return nil
  end
end
```

ruby-samlの場合、更新に失敗すると`nil`を返し、呼び出し側でそれを処理する責任があります。しかし、多くのアプリケーションでは、この`nil`チェックが不十分です。

## フォールバック動作を明示的に設計する

本番環境での停止を防ぐには、メタデータ更新失敗時の動作を明示的に設計・実装する必要があります。

**1. 複数のメタデータソースを用意する**

```ruby
class MetadataManager
  def fetch_metadata
    # 優先順位1：IdPから取得
    metadata = fetch_from_idp
    return metadata if metadata.present?

    # 優先順位2：ローカルキャッシュから取得
    metadata = load_from_cache
    return metadata if metadata.present?

    # 優先順位3：バックアップメタデータから取得
    metadata = load_from_backup
    return metadata if metadata.present?

    # すべて失敗した場合は例外を発生させ、明示的にエラーハンドリングさせる
    raise MetadataUnavailableError, "All metadata sources failed"
  end

  private

  def fetch_from_idp
    # タイムアウト設定を明示的に指定
    response = Net::HTTP.get_response(
      URI(ENV['IDP_METADATA_URL']),
      read_timeout: 5,
      open_timeout: 5
    )
    return nil unless response.code == '200'
    response.body
  rescue Timeout::Error, StandardError => e
    Rails.logger.warn("IdP metadata fetch failed: #{e.message}")
    nil
  end

  def load_from_cache
    # Redisやメモリキャッシュから取得
    Rails.cache.read('saml_metadata')
  end

  def load_from_backup
    # ローカルファイルシステムに保存したバックアップ
    File.read(Rails.root.join('config/saml_metadata_backup.xml'))
  rescue Errno::ENOENT
    nil
  end
end
```

**2. メタデータ更新の失敗を監視可能にする**

```ruby
class MetadataUpdateJob
  include Sidekiq::Worker
  sidekiq_options retry: 5, dead: true

  def perform
    manager = MetadataManager.new
    metadata = manager.fetch_metadata
    
    if metadata.present?
      Rails.cache.write('saml_metadata', metadata, expires_in: 1.hour)
      Rails.cache.write('saml_metadata_updated_at', Time.current)
    else
      # メタデータ更新失敗をアラート
      notify_slack("SAML metadata update failed")
      # ただしジョブは失敗させず、次回の更新を待つ
    end
  rescue MetadataUnavailableError => e
    notify_slack("Critical: All metadata sources exhausted - #{e.message}")
    # この場合は明示的にジョブを失敗させ、アラートを上げる
    raise
  end

  private

  def notify_slack(message)
    # Slack通知の実装
  end
end
```

**3. 認証リクエスト時のメタデータ検証**

```ruby
class SamlController < ApplicationController
  def acs
    # メタデータの鮮度を確認
    metadata_age = Time.current - Rails.cache.read('saml_metadata_updated_at').to_time
    
    if metadata_age > 2.hours
      # メタデータが古い場合は、強制更新を試みる
      MetadataUpdateJob.perform_now
    end

    begin
      response = OneLogin::RubySaml::Response.new(
        params[:SAMLResponse],
        settings: build_saml_settings
      )
      response.is_valid?
    rescue OneLogin::RubySaml::ValidationError => e
      # 署名検証失敗時も、メタデータを強制更新して再試行
      Rails.logger.warn("SAML validation failed: #{e.message}")
      MetadataUpdateJob.perform_now
      redirect_to login_url, alert: "Authentication failed. Please try again."
    end
  end
end
```

## 実務投入時に追加確認すべきポイント

フェデレーション認証を本番環境に投入する前に、以下を確認しておくことで、認証停止の事態を防げます。

**メタデータ更新の周期と監視**

- メタデータ更新ジョブが定期的に実行されているか
- 更新失敗時のログが適切に記録されているか
- アラート設定（メール、Slack等）が機能しているか

**IdPの証明書ローテーション対応**

- IdPが証明書をローテーションするスケジュールを確認
- 事前にテスト環境で新しい証明書での検証をシミュレート
- ローテーション時にメタデータが即座に更新される仕組みを確認
