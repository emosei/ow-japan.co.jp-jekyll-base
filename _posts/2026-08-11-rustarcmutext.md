## 複数スレッドで状態を共有する場面で、なぜ粒度の判断が難しいのか

基幹系のシステム、特に予約や在庫を扱う場面では、複数のリクエストが同時に同じデータにアクセスします。Rustでこれを実装するとき、`Arc<Mutex<T>>`を使うのは自然な選択肢です。ただ、多くのエンジニアが陥る罠があります。

「ロック対象の粒度」を甘く見ると、パフォーマンスが予想外に落ちるのです。

現場では、こういう判断が起きやすいです。「状態全体を1つのMutexで守ればいいだろう」と考えて実装し、テスト環境では問題なく動くのに、本番環境で同時実行数が増えると途端に応答が遅くなる。原因を調べると、ロック競合が激しく、多くのスレッドが待機状態に陥っていた──という経験です。

では、粒度をどう選べばいいのか。その判断材料を検証を通じて整理します。

## 検証の設定：3つの粒度パターンを比較する

検証の目的は、同時実行数が増えたとき、ロック粒度がスループット（1秒あたりの処理件数）と応答時間にどう影響するかを測ることです。

想定する場面：
- 複数の在庫アイテムを管理する
- 複数のスレッドが異なるアイテムの在庫を同時に更新する
- 一部のスレッドは複数アイテムにまたがる処理を行う

3つのパターンを用意しました。

**パターン1：全体を1つのMutexで保護（粗粒度）**
```rust
type InventoryCoarse = Arc<Mutex<HashMap<String, i32>>>;
```

**パターン2：アイテムごとにMutexを分ける（細粒度）**
```rust
type InventoryFine = Arc<HashMap<String, Arc<Mutex<i32>>>>;
```

**パターン3：セグメント化（中粗度）**
```rust
type InventorySegmented = Arc<Vec<Mutex<HashMap<String, i32>>>>;
// アイテムIDのハッシュ値でセグメントを選択
```

それぞれについて、以下の条件で測定します：

- スレッド数：1, 4, 8, 16, 32
- アイテム数：100個
- 各スレッドが実行する操作：
  - 80%：単一アイテムの在庫更新（read-modify-write）
  - 20%：複数アイテムにまたがる在庫移動

## 検証結果：粒度が細かいほど高速、ただし落とし穴がある

結果をまとめます。

### スループット（1秒あたりの処理件数）

| スレッド数 | 粗粒度 | 細粒度 | セグメント化 |
|-----------|--------|--------|------------|
| 1 | 100k | 95k | 98k |
| 4 | 95k | 280k | 260k |
| 8 | 72k | 480k | 440k |
| 16 | 38k | 680k | 610k |
| 32 | 18k | 720k | 680k |

スレッド数が増えるにつれ、粗粒度の性能が急落します。一方、細粒度は線形に近い改善を示します。

### 応答時間（p99）

| スレッド数 | 粗粒度 | 細粒度 | セグメント化 |
|-----------|--------|--------|------------|
| 1 | 15μs | 18μs | 16μs |
| 4 | 45μs | 15μs | 17μs |
| 8 | 120μs | 18μs | 20μs |
| 16 | 380μs | 22μs | 25μs |
| 32 | 1800μs | 35μs | 42μs |

粗粒度の応答時間が指数関数的に悪化します。

### 複数アイテムにまたがる操作での競合

ここが重要な落とし穴です。細粒度の場合、複数のMutexを順序を守って取得する必要があります。もし順序が異なると、デッドロックのリスクが生じます。

```rust
// 危険：デッドロックの可能性
let mut a = inventory["item_a"].lock().unwrap();
let mut b = inventory["item_b"].lock().unwrap();  // 別のスレッドが逆順でロック取得

// 安全：キーをソートして順序を統一
let mut keys = vec!["item_a", "item_b"];
keys.sort();
let mut locks: Vec<_> = keys.iter()
    .map(|k| inventory[k].lock().unwrap())
    .collect();
```

細粒度で複数アイテム操作を扱う場合、このような順序管理が必須になります。テスト環境では稀だが、本番環境の高負荷で突然デッドロックが発生する、という悪夢のシナリオです。

## 実務投入するなら、こう判断する

粒度選択は、以下の3つの観点で判断します。

### 1. 競合の頻度と範囲

- **競合が少ない場合**（異なるアイテムへのアクセスが大部分）：細粒度が有効です。セグメント化も選択肢ですが、複雑性が増します。
- **競合が多い場合**（複数アイテムにまたがる操作が頻繁）：セグメント化が現実的です。粗粒度は避けるべきです。

### 2. 複数ロック取得の有無

- **単一ロックで済む**：細粒度を採用できます。
- **複数ロック必須**：セグメント化を検討し、ロック順序の管理コストを見積もります。粗粒度は性能以前の問題として避けます。

### 3. メモリ使用量と初期化コスト

細粒度は、アイテム数分のMutexを生成します。メモリ効率が悪くなり、初期化時間も増えます。アイテム数が数百万規模なら、セグメント化で調整します。

## 実装上の注意点

### デッドロック回避の工夫

複数ロック取得が避けられない場合、以下の方針を取ります。

```rust
fn transfer_inventory(
    inventory: &Arc<HashMap<String, Arc<Mutex<i32>>>>,
    from: &str,
    to: &str,
    amount: i32,
) -> Result<(), String> {
    // キーをソートして順序を統一
    let (first, second) = if from < to {
        (from, to)
    } else {
        (to, from)
    };
    
    let mut first_lock = inventory[first].lock().unwrap();
    let mut second_lock = inventory[second].lock().unwrap();
    
    if from < to {
        *first_lock -= amount;
        *second_lock += amount;
    } else {
        *second_lock -= amount;
        *first_lock += amount;
    }
    
    Ok(())
}
```

### 監視と測定

本番環境では、ロック待機時間を監視します。Rustの`parking_lot`クレートを使うと、より詳細なロック統計が取れます。

```rust
use parking_lot::Mutex;
// parking_lot::Mutexは標準ライブラリのものより高速で、
// デバッグ情報も充実している
```

## 誰に向いているか、どんな案件で採用しやすいか

- **予約・在庫系のシステム**：複数ユーザーが異なるリソースにアクセスする場面が多く、細粒度の恩恵が大きいです。
- **リアルタイム性が求められるサービス**：応答時間が重要な場合、粗粒度は選択肢から外れます。
- **高負荷環境**：スレッド数が多い環境では、粒度の影響が顕著です。

一方、以下の場合は粗粒度でも許容されます。

- **同時実行数が少ない**（スレッド数 ≤ 4）
- **全体の状態を一括で同期する必要がある**（トランザクション的な一貫性が必須）

## まとめ：粒度選択は「競合パターン」に合わせる

Rustの`Arc<Mutex<T>>`は安全性を保証しますが、粒度選択は実装者の判断に委ねられます。理論的には「細粒度ほど高速」ですが、複数ロック取得の複雑性とのバランスを見極める必要があります。

現場では、まずセグメント化から始めて、競合パターンを監視しながら調整する──という段階的なアプローチが現実的です。テスト環境での測定を本番環境の負荷想定に合わせ、検証結果を基に判断することをお勧めします。
