## 現場で避けられない「トランザクションが長引く」という現実

基幹系のWebアプリケーション、特に予約や受注、在庫管理といった業務では、ユーザーが画面に向き合っている時間そのものがトランザクションの一部になってしまうことがあります。ユーザーが検索結果を眺めながら判断を下し、複数の条件を入力し直し、最後に確定ボタンを押すまで、その間ずっとデータベースのロックが保持されたままになるケースです。

数秒で完結するトランザクション設計が理想ですが、現場ではそうもいきません。商品の詳細情報を取得し、在庫を確認し、顧客情報を引き出し、割引ルールを適用し、最後に注文を確定する──この一連の流れが、ユーザーの操作時間を含めて30秒以上になることは珍しくありません。

そうなると、複数ユーザーが同じ在庫に対してアクセスしたときに「ロック競合」が起きやすくなります。一人目のユーザーがロックを保持したまま悩んでいる間に、二人目、三人目のユーザーが待たされ、やがてタイムアウトやデッドロックが発生する──という悪循環です。

この記事では、そうした状況下で「ロック競合を早期に検出し、ユーザーに分かりやすく伝え、必要に応じて緩和する」実装パターンを、Rubyの実装例を交えて検証します。

## 検証の前提と比較観点

まず、検証の枠組みを整理します。

**前提条件:**
- Rails環境でPostgreSQLを使用
- 複数ユーザーが同時に同じ在庫レコードにアクセスするシナリオ
- トランザクション分離レベルは `READ COMMITTED`（一般的な設定）
- ユーザー操作を含めたトランザクション時間は10～60秒程度

**比較する3つのアプローチ:**

1. **悲観的ロック（Pessimistic Lock）**: データ取得時にロックを掛ける。競合を完全に防ぐが、スケーラビリティが低い
2. **楽観的ロック（Optimistic Lock）**: バージョン番号で競合を検出。スケーラビリティは高いが、ユーザーが「失敗」を受け取る
3. **ロック競合の早期検出 + 段階的緩和**: 悲観的ロックの一部を活用しつつ、競合を事前に通知し、ユーザーに判断させる

この記事では、3番目のアプローチに焦点を当てます。

## 実装パターン1: ロック保持時間を分割する

長いトランザクションを複数の短いトランザクションに分割することで、ロック競合の窓口を狭めるのが第一歩です。

```ruby
class OrderService
  def place_order(user_id, items)
    # ステップ1: 在庫確認（短時間のロック）
    inventory_lock = check_inventory_with_lock(items)
    return { success: false, reason: 'out_of_stock' } unless inventory_lock

    # ステップ2: ユーザー入力を受け取る（ロックなし）
    # 実際の画面では、ここでユーザーが住所や支払方法を選択
    order_data = build_order_data(user_id, items)

    # ステップ3: 最終確定（再度ロック）
    begin
      confirm_order_with_lock(user_id, order_data)
      { success: true }
    rescue Mysql2::Error::LockWaitTimeoutError
      { success: false, reason: 'lock_timeout', retry_after: 5 }
    end
  end

  private

  def check_inventory_with_lock(items)
    Inventory.transaction do
      items.all? do |item|
        inv = Inventory.lock.find_by(product_id: item[:id])
        inv && inv.quantity >= item[:amount]
      end
    end
  end

  def confirm_order_with_lock(user_id, order_data)
    Order.transaction do
      # 再度在庫を確認してから確定
      order_data[:items].each do |item|
        inv = Inventory.lock.find(item[:id])
        inv.update!(quantity: inv.quantity - item[:amount])
      end
      Order.create!(order_data)
    end
  end
end
```

**利点:**
- ロック保持時間が短いため、競合の確率が下がる
- 設計がシンプルで、既存コードへの影響が小さい

**制約:**
- 「確認時点」と「確定時点」で在庫が変わる可能性がある（二重予約のリスク）
- ユーザーが途中で離脱した場合、確認結果が無効になる

## 実装パターン2: 競合を検出してユーザーに通知する

ロック競合が起きたときに、単に「エラー」と返すのではなく、ユーザーに状況を説明し、再試行を促すアプローチです。

```ruby
class OrderService
  LOCK_TIMEOUT_SECONDS = 5
  MAX_RETRY_ATTEMPTS = 3

  def place_order_with_retry(user_id, items)
    retry_count = 0

    begin
      Inventory.transaction(isolation: :serializable) do
        items.each do |item|
          inv = Inventory.lock.find(item[:id])
          raise InsufficientInventoryError if inv.quantity < item[:amount]
          inv.update!(quantity: inv.quantity - item[:amount])
        end

        Order.create!(
          user_id: user_id,
          items: items,
          status: 'confirmed'
        )
      end

      { success: true, message: '注文が確定しました' }

    rescue ActiveRecord::LockWaitTimeoutError => e
      retry_count += 1
      if retry_count < MAX_RETRY_ATTEMPTS
        # 指数バックオフで再試行
        sleep(0.5 * (2 ** retry_count))
        retry
      else
        {
          success: false,
          reason: 'lock_timeout',
          message: '他のユーザーが処理中です。しばらく待ってから再度お試しください。',
          retry_after: 10,
          can_retry: true
        }
      end

    rescue InsufficientInventoryError
      {
        success: false,
        reason: 'out_of_stock',
        message: '申し訳ありません。在庫がなくなってしまいました。',
        can_retry: false
      }
    end
  end
end
```

**ポイント:**
- `isolation: :serializable` で最も厳しい分離レベルを使用
- ロック競合時に自動で指数バックオフ再試行
- ユーザーに「再試行可能か」「待つべき時間」を明確に返す

**フロントエンド側の実装例:**

```javascript
async function submitOrder(items) {
  const response = await fetch('/orders', {
    method: 'POST',
    body: JSON.stringify({ items })
  });

  const result = await response.json();

  if (result.success) {
    showMessage('注文完了', 'success');
    redirectToConfirmation();
  } else if (result.reason === 'lock_timeout' && result.can_retry) {
    showMessage(result.message, 'warning');
    setTimeout(() => {
      submitOrder(items); // 自動再試行
    }, result.retry_after * 1000);
  } else {
    showMessage(result.message, 'error');
  }
}
```

**利点:**
- ユーザーが状況を理解できる
- 自動再試行により、一時的な競合を吸収できる
- エラーハンドリングが明確

**制約:**
- 自動再試行が多発すると、データベースに負荷がかかる
- ユーザーが長く待たされる可能性がある

## 実装パターン3: 段階的なロック戦略

「読み取り」と「書き込み」のロック段階を分けることで、競合を緩和するアプローチです。

```ruby
class AdvancedOrderService
  def place_order_staged(user_id, items)
    # ステージ1: 読み取りロック（他の読み取りは許可）
    order_preview = Inventory.transaction do
      items.map do |item|
        inv = Inventory.lock('FOR SHARE').find(item[:id])
        {
          product_id: item[:id],
          requested: item[:amount],
          available: inv.quantity,
          can_fulfill: inv.quantity >= item[:amount]
        }
      end
    end

    # ステージ2: 確認結果をユーザーに返す
    return { success: false, preview: order_preview } unless order_preview.all? { |p| p[:can_fulfill] }

    # ステージ3: 書き込みロック（確定時のみ）
    begin
      Inventory.transaction do
        items.each do |item|
          inv = Inventory.lock('FOR UPDATE').find(item[:id])
          raise InsufficientInventoryError if inv.quantity < item[:amount]
          inv.update!(quantity: inv.quantity - item[:amount])
        end

        Order.create!(user_id: user_id, items: items, status: 'confirmed')
      end

      { success: true, preview: order_preview }

    rescue ActiveRecord::LockWaitTimeoutError
      {
        success: false,
        reason: 'write_lock_timeout',
        preview: order_preview,
        message: '確定処理に時間がかかっています。もう一度お試しください。'
      }
    end
  end
end
```

**PostgreSQL固有の構文:**
- `FOR SHARE`: 他の読み取りロックとは共存するが、書き込みロックはブロック
- `FOR UPDATE`: 排他的ロック

**利点:**
- 読み取り段階で複数ユーザーが並行処理できる
- 書き込みロックは最短時間に限定される
- 競合の確率が大幅に低下

**制約:**
- PostgreSQL固有の機能を使うため、他のDBMSへの移行が困難
- ロック戦略の複雑さが増す
