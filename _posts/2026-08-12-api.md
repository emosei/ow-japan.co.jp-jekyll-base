## 問題の構図

テスト環境では正常に動作するAPIの認証処理が、本番環境のロードバランサー配下で間欠的に失敗する。ログを見ると、クライアントから送信された `Authorization` ヘッダーが時々 `authorization` に変わっている。認証ロジック自体は大文字小文字を区別していないはずなのに、なぜ失敗するのか。

こういう状況は、実装チーム内で「環境差分の確認漏れ」と「HTTPヘッダーの仕様理解の甘さ」が重なるときに起きやすいです。一度原因を理解しておくと、設計レビューの段階で防ぎやすくなります。

## HTTPヘッダーの大文字小文字は「本来は区別しない」

まず押さえておくべき前提として、RFC 7230 では HTTPヘッダーの**名前**は大文字小文字を区別しません。`Authorization`、`authorization`、`AUTHORIZATION` はすべて同じヘッダーを指します。

一方、ヘッダーの**値**については、仕様で明示されていない限り大文字小文字を区別する可能性があります。たとえば Bearer トークンの値自体は、生成方式によって大文字小文字を含む場合があり、その値の正確さが重要です。

この「ヘッダー名は正規化される」という前提が、実装者の間で共有されていないと、以下のような不整合が生まれます。

```
// テスト環境：アプリケーションサーバーが直接受け取る
クライアント → Authorization: Bearer xxx → アプリケーション
（ヘッダー名は Authorization のまま）

// 本番環境：ロードバランサーを経由
クライアント → Authorization: Bearer xxx → ロードバランサー → authorization: Bearer xxx → アプリケーション
（ロードバランサーが小文字に正規化）
```

## ロードバランサーが正規化する理由

一般的なロードバランサー（nginx、HAProxy、クラウドプロバイダーのALB/NLBなど）の多くは、パフォーマンスやログ解析の都合で、HTTPヘッダーを**内部的に小文字に正規化**する動作をしています。

理由としては：

- **メモリ効率**：ヘッダー名の重複排除やキャッシュ時に、正規化されたキーの方が扱いやすい
- **ログ・監視の一貫性**：WAFやアクセスログ解析で、ヘッダー名の揺らぎを吸収したい
- **HTTP/2 対応**：HTTP/2では全ヘッダー名が小文字に正規化される仕様

つまり、ロードバランサー配下のアプリケーションが受け取るヘッダーは、**常に小文字になる可能性が高い**ということです。

## テスト環境で気づきにくい理由

開発環境やテスト環境では、アプリケーションサーバーが直接クライアントと通信することが多いため、ロードバランサーの正規化が入りません。結果として、クライアントが送信したままのヘッダー形式（通常は `Authorization` など）が保持されます。

実装者は「認証ロジックが大文字小文字を区別していないから大丈夫」と考えがちですが、実際に問題になるのは以下のケースです：

- **ヘッダー名を文字列キーで直接参照している**場合、`request.headers['Authorization']` が `None` や `undefined` を返す
- **ヘッダーダンプやログ出力時に、期待するキー名と一致しない**
- **外部ライブラリやミドルウェアが、特定の大文字形式を前提にしている**

## 実装レベルでの対策

### 1. ヘッダー取得時は常に大文字小文字を区別しない

```python
# Django の例
auth_header = request.META.get('HTTP_AUTHORIZATION') or request.META.get('HTTP_authorization')

# または、より安全に
import re
for key, value in request.META.items():
    if key.lower() == 'http_authorization':
        auth_header = value
        break
```

```javascript
// Node.js / Express の例
const authHeader = req.get('Authorization') || req.get('authorization');

// Express は内部で大文字小文字を吸収するが、明示的に対応
```

### 2. フレームワークの標準メソッドを活用

ほとんどのWebフレームワークは、ヘッダー取得時に大文字小文字を自動的に正規化する仕組みを持っています。

- **Django**：`request.META.get()` は HTTP_ プレフィックスを付けた大文字キーで取得するが、内部で正規化
- **Rails**：`request.headers['Authorization']` は大文字小文字を区別しない
- **Express**：`req.get()` メソッドは大文字小文字を区別しない

**重要なのは、フレームワークのドキュメントで「ヘッダー取得の正規形」を確認し、それに統一すること**です。

### 3. 認証ミドルウェアで一度だけ正規化

```python
# Django middleware の例
class AuthHeaderNormalizationMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response
    
    def __call__(self, request):
        # ロードバランサーが小文字にした可能性があるため、
        # ここで標準形（大文字）に統一してから処理を進める
        auth_value = None
        for key in request.META:
            if key.lower() == 'http_authorization':
                auth_value = request.META[key]
                break
        
        if auth_value:
            request.META['HTTP_AUTHORIZATION'] = auth_value
        
        return self.get_response(request)
```

この方法は、認証ロジック全体で「常に大文字形式」を前提できるメリットがあります。

## 設定・運用の観点

### ロードバランサーの動作確認

本番環境への投入前に、必ず確認すべき項目：

- **ロードバランサーの正規化設定**：nginx なら `proxy_pass_request_headers on;` で上流サーバーにヘッダーを渡す際の形式を確認
- **ALB/NLB の場合**：AWS ドキュメントで「ヘッダー名の正規化」が明示されているか確認
- **WAF や API Gateway を経由する場合**：各レイヤーでの正規化動作を個別に確認

### テスト環境での再現

本番環境と同じロードバランサー構成をテスト環境に用意し、実際にヘッダーがどう変わるかをダンプして確認します。

```bash
# curl で Authorization ヘッダーを送信し、
# サーバー側でどう受け取られるか確認
curl -H "Authorization: Bearer test_token" http://loadbalancer/api/test

# サーバーログで受け取ったヘッダー形式を記録
```

### 統合テストでの検証

ロードバランサーを経由した場合と直接アクセスした場合の両方で、認証が成功することを確認するテストケースを追加します。

```python
# テスト例
def test_auth_header_case_insensitive():
    # ロードバランサーが小文字にした場合
    response = client.get(
        '/api/protected',
        HTTP_AUTHORIZATION='Bearer valid_token'
    )
    assert response.status_code == 200
    
    # 大文字の場合
    response = client.get(
        '/api/protected',
        HTTP_AUTHORIZATION='Bearer valid_token'
    )
    assert response.status_code == 200
```

## 実装の判断ポイント

### どのレイヤーで対応するか

**推奨：ミドルウェア層で一度だけ正規化**

理由は：
- 認証ロジック全体で統一した前提が持てる
- 複数の認証方式（Basic、Bearer、Digest など）に対応しやすい
- テストも集中管理できる

**避けるべき：各認証ロジック内で個別に対応**

理由は：
- 対応漏れが生じやすい
- 保守性が低下する
- 新しい認証方式追加時に毎回対応が必要

### 外部ライブラリ依存時の注意

OAuth2 ライブラリや JWT 検証ライブラリが、ヘッダー取得時に特定の大文字形式を前提にしていないか、事前に確認します。ほとんどの成熟したライブラリは対応していますが、古いバージョンや小規模なライブラリでは落とし穴になります。

## まとめ

本番環境のロードバランサーがヘッダーを正規化する動作は、HTTP仕様に準拠した正当な動作です。問題は、テスト環境ではこの正規化が起きないため、実装者がそれに気づかないことです。

対策として重要なのは：

1. **フレームワークの標準メソッドを信頼する**：大文字小文字の吸収は設計済みのケースが多い
2. **ミドルウェア層で一度だけ正規化する**：認証ロジック全体の前提を統一する
3. **本番環境と同じ構成でテストする**：ロードバランサー経由でのヘッダー形式を実際に確認する

小規模なチームほど「テスト環境と本番環境の構成差分」を見落としやすいですが、認証は信頼性が重要な領域です。投入前の確認を丁寧にしておくと、本番での問題を大幅に減らせます。
