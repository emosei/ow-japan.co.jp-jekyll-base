## 外部サービス障害時の「保護」と「対応」のズレ

外部APIやマイクロサービスとの連携が増える中で、サーキットブレーカーパターンの導入は一般的になりました。依存先サービスが異常状態に陥ったとき、リクエストを遮断してサーバー側の過負荷を防ぐ──これ自体は正しい防御です。

ただ、現場ではこういう場面に出くわします。

サーキットブレーカーが正常に動作し、外部サービスへのリクエストが遮断されているのに、ユーザーへの影響が思わしくない。エラーメッセージがバラバラ、一部の機能は動き一部は止まる、キャッシュされたデータと新鮮なデータが混在する──こうした『部分的な不具合』が散発的に報告される。

問題の根本は、サーバー側の保護と、クライアント側のフォールバック処理の間に「粒度のズレ」が生まれているからです。

## サーキットブレーカーとフォールバック処理は別の責任

サーキットブレーカーパターンは、外部依存先の障害からサーバー自身を守る仕組みです。リクエストが一定数失敗したら、以降のリクエストを即座に失敗させて、サーバーのリソース（スレッド、接続プール、メモリ）の枯渇を防ぎます。

一方、フォールバック処理はクライアント側の責任です。外部サービスが使えない状況で、アプリケーション全体がどう振る舞うかを決めるものです。

実装の現場では、この分離が曖昧になりやすいです。

```
サーバー側: 外部APIへのリクエストが失敗
  → サーキットブレーカーが開く
  → クライアントに「503 Service Unavailable」を返す

クライアント側: 503を受け取った
  → キャッシュがあれば使う？
  → 古いデータを表示する？
  → エラー画面を出す？
  → 再試行する？
```

ここで、各クライアント（Webフロントエンド、モバイルアプリ、バックオフィスツール）が独立した判断をしてしまうと、ユーザーが見る画面は統一性を失います。

## 「機能ごと」「画面ごと」に異なるフォールバック戦略が散在する

典型的な状況を挙げます。

あるサービスが、ユーザー情報、注文履歴、推奨商品の3つの外部APIに依存しているとします。

- **ユーザー情報API**が落ちた場合：ログイン状態が確認できないので、ユーザーを一度ログアウトさせるべき
- **注文履歴API**が落ちた場合：過去データはキャッシュで十分。『最新情報は取得できていません』という注釈をつけて古いデータを表示
- **推奨商品API**が落ちた場合：そもそも『あると便利』機能なので、その欄を非表示にすればよい

それぞれのエンドポイントに対して個別のサーキットブレーカーを立てるのは正しい判断です。しかし、クライアント側がこの違いを認識していなければ、すべてのエラーを同じ方法で処理してしまいます。結果、推奨商品が出ないだけで注文履歴も古いデータになり、ユーザーは『何か調子が悪い』という印象を受けます。

## 粒度のズレが生むもう一つの問題：非同期リトライの増加

さらに厄介なのが、クライアント側で『エラーハンドリングが不完全』な場合です。

Webフロントエンド（SPA）やモバイルアプリでは、外部APIのエラーに対して自動リトライロジックが組み込まれることがあります。特にネットワーク不安定な環境では、一時的なエラーと永続的な障害を区別しにくいため、「とりあえず再試行する」という実装になりやすいです。

サーキットブレーカーがサーバー側で開いているのに、クライアント側が知らずに再試行を続ける。これは前の記事で触れた「バックオフ競争」と似た現象ですが、より深刻です。なぜなら、複数のクライアント（Web、iOS、Android、API連携先など）が独立して再試行を始めるからです。

結果として、サーバー側のサーキットブレーカーが開いているはずなのに、ログには『リクエストが殺到している』という矛盾した状態が記録されます。

## では、どう設計するか

### 1. サーキットブレーカーの状態をクライアントに明示する

サーバーがサーキットブレーカーを開いたとき、単に「503」を返すだけでなく、レスポンスヘッダやボディに『どの外部サービスが落ちているのか』を含めるべきです。

```json
{
  "error": "service_unavailable",
  "failed_service": "user_profile_api",
  "retry_after": 60,
  "fallback_strategy": "use_cache"
}
```

クライアント側は、このメタデータを読んで、機能ごとに適切なフォールバック処理を選択できます。

### 2. フォールバック戦略をドキュメント化して共有する

「このAPIが落ちたら、こう動く」というルールを、サーバー側で定義してドキュメント化します。クライアント開発チームはそれを読んで実装します。

曖昧な指示（『エラーハンドリングをよろしく』）ではなく、具体的な指針が必要です。

- キャッシュを使うなら、何秒まで古いデータを許容するのか
- エラー画面を出すなら、どのテキストを表示するのか
- 再試行するなら、何回まで、どの間隔で行うのか

### 3. 機能の重要度で段階的に対応する

すべての外部依存先に同じレベルの保護を用意する必要はありません。

- **Critical**（ユーザー認証など）：フォールバック不可。エラー画面を出して機能停止
- **Important**（注文情報など）：キャッシュで対応。『古いデータです』と明示
- **Nice to have**（推奨商品など）：機能ごと非表示。ユーザーに影響なし

この分類に応じて、クライアント側の実装複雑度も変わります。

### 4. 運用段階で『フォールバック動作』をテストしておく

本番環境でサーキットブレーカーが開いたとき、実際にクライアントがどう動くかを事前に検証しておくことが重要です。

- ステージング環境で外部APIを意図的に遮断して、動作を確認
- 複数のクライアント（Web、モバイル、バッチ処理など）を同時にテスト
- ユーザーに見える画面がどうなるか、複数パターン確認

## 中小規模チームが現実的に取れるアクション

大規模な組織であれば、サーキットブレーカーの状態管理専用のサービスを作ることもあります。ただ、そこまでの投資が難しい場合は、以下の順序で進めるとよいです。

1. **まずは外部API呼び出しごとにサーキットブレーカーを分ける**（すでにやっているなら次へ）
2. **エラーレスポンスに『何が落ちているか』の情報を含める**
3. **クライアント側で機能ごとのフォールバック処理を明示的に実装する**（ハードコードでもいいので）
4. **定期的にフォールバック動作をテストする**（手動でもいいので）

サーキットブレーカーはサーバーの過負荷を防ぎますが、ユーザー体験を守るのはクライアント側の責任です。その責任を明確にして、実装に反映させることが、結果として安定したシステムにつながります。
