## 現場で起きている判断の難しさ

Railsプロジェクトでgemをアップデートするとき、変更ログを読んで「これなら互換性がありそう」と判断しても、本番環境で思わぬ挙動が出る経験は多いのではないでしょうか。

その原因の一つは、モデル層の責務が曖昧だと、外部ライブラリの変更が「どこまで影響するのか」を正確に予測できなくなることです。

たとえば、ユーザー認証関連のgemをマイナーバージョンアップしたとき、モデルに埋め込まれた複数の責務（バリデーション、暗号化、ログ出力、外部APIとの連携）が絡み合っていると、テストケースを通過しても実運用で問題が出やすくなります。「どの責務がgemの変更の影響を受けるのか」が不明確だからです。

この記事では、モデルの責務境界が曖昧なときに起こる互換性判定の複雑化と、その対策について、実装と運用の両面から考えます。

## 責務が混在したモデルが招く「見えない依存関係」

### 典型的なパターン

Railsモデルは、ActiveRecordのメソッドとビジネスロジックが一緒に住む場所です。この性質自体は悪くないのですが、問題は「何がモデルに属するのか」の線引きが曖昧になりやすいことです。

以下のようなモデルを考えてみてください。

```ruby
class User < ApplicationRecord
  has_many :orders
  
  # 1. バリデーション
  validates :email, presence: true, uniqueness: true
  validates :password, length: { minimum: 8 }
  
  # 2. 認証ロジック（外部gemに依存）
  has_secure_password
  
  # 3. 暗号化（別のgem）
  encrypt :ssn, deterministic: true
  
  # 4. 外部API連携（ユーザー情報を外部サービスに送信）
  after_create :notify_external_service
  
  # 5. ログ・監査
  after_update :log_changes
  
  # 6. キャッシュ無効化
  after_save :invalidate_cache
  
  def notify_external_service
    ExternalAPI.register_user(self)
  end
  
  def log_changes
    AuditLog.record(self, changes)
  end
  
  def invalidate_cache
    Rails.cache.delete("user:#{id}")
  end
end
```

このモデルでは、複数のgemが複数の責務に影響を与えています。

- 認証関連gemがバージョンアップ → `has_secure_password` の動作が変わる可能性
- 暗号化gemがバージョンアップ → `encrypt` の動作が変わる可能性
- キャッシュ戦略が変わると → `invalidate_cache` の実装を見直す必要

これらが全てモデルに入っていると、「このgemのアップデートは安全か？」を判定するために、モデル全体を読み込んで、すべての依存関係を追跡しなければなりません。

### なぜ互換性判定が複雑になるのか

ライブラリのChangelogを読むと、多くの場合「戻り値の型が変わった」「コールバックのタイミングが変わった」「エラー処理が厳しくなった」といった情報が書かれています。

しかし、モデルの責務が混在していると、その変更が「実際にはどの処理に影響するのか」が追跡困難になります。

- 認証gemが「ハッシュアルゴリズムの検証を厳しくした」 → これはバリデーション層に影響するのか、ログ層に影響するのか？
- キャッシュライブラリが「キー形式を変更した」 → これは `invalidate_cache` だけに影響するのか、他の処理にも波及するのか？

結果として、テストケースの数が指数関数的に増えます。

## 責務を分離する設計アプローチ

### 層別の責務分離

現場では完全な責務分離は難しいことが多いですが、少なくとも「外部ライブラリに依存する部分」と「ビジネスロジック」を分ける工夫が有効です。

```ruby
# app/models/user.rb
class User < ApplicationRecord
  has_many :orders
  
  # モデル自身の責務：データベーススキーマに関わることだけ
  validates :email, presence: true, uniqueness: true
  validates :password_digest, presence: true
  
  # 認証・暗号化は専用クラスに委譲
  delegate :authenticate, to: :authenticator
  delegate :encrypted_ssn, to: :encryptor
  
  def authenticator
    @authenticator ||= UserAuthenticator.new(self)
  end
  
  def encryptor
    @encryptor ||= UserEncryptor.new(self)
  end
end

# app/services/user_authenticator.rb
class UserAuthenticator
  def initialize(user)
    @user = user
  end
  
  # 認証ロジック（has_secure_passwordに依存）
  def authenticate(password)
    # BCryptやその他の認証gemの依存はここに閉じ込める
    BCrypt::Password.new(@user.password_digest) == password
  end
end

# app/services/user_encryptor.rb
class UserEncryptor
  def initialize(user)
    @user = user
  end
  
  # 暗号化ロジック（encryptiongemに依存）
  def encrypted_ssn
    # 暗号化gemの依存はここに閉じ込める
  end
end

# app/services/user_event_handler.rb
class UserEventHandler
  def self.on_create(user)
    notify_external_service(user)
    log_creation(user)
    invalidate_cache(user)
  end
  
  def self.on_update(user)
    log_changes(user)
    invalidate_cache(user)
  end
  
  private
  
  def self.notify_external_service(user)
    ExternalAPI.register_user(user)
  end
  
  def self.log_changes(user)
    AuditLog.record(user, user.previous_changes)
  end
  
  def self.invalidate_cache(user)
    Rails.cache.delete("user:#{user.id}")
  end
end
```

そして、モデルのコールバックはイベントハンドラに委譲します。

```ruby
class User < ApplicationRecord
  after_create { UserEventHandler.on_create(self) }
  after_update { UserEventHandler.on_update(self) }
end
```

### この設計のメリット

1. **互換性判定が局所化される**  
   認証gemがアップデートされた → `UserAuthenticator` だけを確認すればよい

2. **テストが書きやすくなる**  
   各責務ごとに独立したテストを書けるため、テストケースが線形で済む

3. **ライブラリ変更の影響範囲が明確**  
   「このgemの変更は、どのサービスクラスに影響するのか」が一目瞭然

## 運用時のハマりやすいポイント

### 段階的な移行時の注意

既存のプロジェクトでこの分離を進める場合、全てを一度に書き換えるのは現実的ではありません。段階的に進めるときの注意点を挙げます。

**古いモデルと新しいサービスクラスが共存する期間**

```ruby
class User < ApplicationRecord
  # 古い方法（モデル内にロジックがある）
  after_create :notify_external_service_old
  
  # 新しい方法（サービスクラスに委譲）
  after_create { UserEventHandler.on_create(self) }
  
  def notify_external_service_old
    # 古い実装...
  end
end
```

この状態では、外部サービスへの通知が二重に走る可能性があります。必ず古い実装を削除してから新しい方法に切り替えてください。

### テスト環境での落とし穴

責務を分離したとき、テスト環境でgemをモックしやすくなります。しかし、本番環境ではそのgemが実際に動作します。

```ruby
# テスト
it 'ユーザーが作成される' do
  allow(UserEventHandler).to receive(:on_create)
  user = User.create(email: 'test@example.com', password: 'secure_password')
  expect(user).to be_persisted
end
```

このテストは通るかもしれませんが、本番で外部APIが遅い場合、タイムアウトが発生する可能性があります。外部API呼び出しは、さらに非同期処理（ActiveJobなど）に分離することを検討してください。

## 小規模チームでも始めやすい実装ステップ

1. **最初は「外部ライブラリに依存する部分」だけを分離する**  
   認証、暗号化、キャッシュなど、gemに直結する責務から始める

2. **コールバックをサービスクラスに集約する**  
   `after_create`, `after_update` などをモデルから削除し、サービスクラスに集約

3. **テストを書き換える**  
   モデルのテストから、サービスクラスのテストに移行

4. **Changelogを読むときの判定基準を変える**  
   「モデル全体への影響」ではなく、「どのサービスクラスに影響するのか」で判定

## まとめ

Railsモデルの責務が曖昧だと、外部ライブラリのバージョンアップ時に互換性判定の複雑さが指数関数的に増します。

モデルに複数の責務が混在していると、「このgemの変更は安全か？」という判定が、モデル全体の読み込みと全ての依存関係の追跡を必要とします。結果として、テストケースも増え、運用の負担が大きくなります。

責務を分離することで、互換性判定は局所化され、テストも書きやすくなり、何より「どのgemの変更がどの部分に影響するのか」が明確になります。既存プロジェクトであれば、段階的に進めることで、無理なく改善できます。
