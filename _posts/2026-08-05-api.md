## 現場で起きている現象

APIサーバーに負荷が高まってきたので、レート制限を導入しようという判断は自然なものです。ただ、既に運用中のシステムに後付けする場合、予想外の問題が生じることがあります。

それは、既存クライアント側が独自に実装してきた再試行ロジックが、新しく設定されたレート制限と相互作用を始めるという現象です。結果として、本来は負荷を抑えるはずのレート制限導入が、むしろサーバーへのリクエスト総数を増やしてしまうケースがあるのです。

この問題は、レート制限の仕様だけを決めて導入すると見落としやすい、実装と運用の接合部で起こる課題です。

## なぜ『バックオフ競争』が発生するのか

まず、既存システムの状況を想定してみましょう。

複数のクライアント（Webアプリ、モバイルアプリ、バッチ処理など）がAPIを呼び出しています。これらのクライアントは、ネットワーク遅延やサーバーエラーに備えて、各々が独自の再試行ロジックを持っています。典型的には「失敗したら指数バックオフで待機してから再試行」という実装です。

ここにレート制限を導入すると、以下の流れが起きます。

1. **レート制限に達すると、サーバーは 429 Too Many Requests を返す**
2. **クライアント側の再試行ロジックが発動する**
   - 「サーバーが応答できない状態だ」と判定
   - バックオフ戦略に従って待機時間を計算
   - その後、リクエストを再送信
3. **複数クライアントが同時に再試行を開始する**
   - 待機時間が重ならないと、ほぼ同じタイミングで再試行が集中
   - その結果、レート制限の枠を超えるリクエストが殺到
4. **サーバーは再び 429 を返す**
5. **各クライアントが再度バックオフして再試行……**

この悪循環が、複数クライアントで並行して起きるのです。個々のクライアントの再試行ロジックは理に適っていても、全体では『バックオフ競争』という名の干渉現象になってしまいます。

## 実装側で見落としやすい点

レート制限を実装する側は、通常こう考えます。

「1秒間に100リクエストまで」という制限を設定すれば、サーバーの負荷は抑えられるはずだ、と。

しかし現実には：

- **既存クライアントの再試行戦略が、制限値の想定を崩す**
  - 指数バックオフの初期待機時間が短い（例：100ms）場合、複数クライアントの再試行が数秒以内に集中しやすい
  - 結果、制限時間窓内に予定外の高いリクエスト密度が生じる

- **クライアント側で『成功するまで再試行』という実装が多い**
  - 最大試行回数に上限がない、あるいは上限が大きい
  - ネットワーク遅延と 429 の区別がつかないため、どちらでも同じロジックで対応

- **バックオフの『ジッター』がない場合、さらに集中しやすい**
  - クライアント A、B、C が同じタイミングで 429 を受けて、同じ待機時間で再試行
  - サーバー側のレート制限ウィンドウと、クライアント側の再試行タイミングが共鳴

## 設計段階での判断ポイント

後付けレート制限を導入する際、以下の点を事前に確認・調整する必要があります。

### 既存クライアントの再試行ロジックを把握する

- 各クライアント（Webフロントエンド、モバイルアプリ、バッチなど）が、どういう再試行ロジックを持っているか
- 最大試行回数、バックオフの計算式、ジッターの有無
- 429 エラーに対して、他のエラーと同じ扱いをしているか、特別扱いしているか

この情報がないと、レート制限の値を決めようがありません。

### サーバー側で『Retry-After』ヘッダーを返す

HTTP 429 レスポンスに `Retry-After` ヘッダーを含めることで、クライアント側に「この時間待ってから再試行してほしい」という指示を明示できます。

```
HTTP/1.1 429 Too Many Requests
Retry-After: 2
Content-Type: application/json

{"error": "Rate limit exceeded"}
```

クライアント側の再試行ロジックが、このヘッダーを読んで待機時間を決めるように実装されていれば、バックオフ競争の頻度を減らせます。

ただし、既存クライアントがこのヘッダーに対応していない場合、導入効果は限定的です。

### 段階的な導入と監視

レート制限を一気に本番投入するのではなく：

1. **ステージング環境で、実際のクライアントを相手にテストする**
2. **本番環境でも、最初は制限値を緩く設定する**
3. **リクエスト分布、エラー率、再試行の頻度を監視**
4. **データに基づいて、制限値を徐々に厳しくしていく**

この過程で、予想外の再試行パターンが顕在化することがあります。

## 中小規模チームが現実的に取れるアクション

すべてのクライアントを一度に改修するのは現実的ではありません。以下のような段階的アプローチが実務的です。

1. **まずクライアント側の再試行ロジックを『可視化』する**
   - ログに「何回目の再試行か」「待機時間はいくつか」を記録
   - 本番環境でのレート制限導入後、再試行の頻度や分布を観察

2. **Retry-After ヘッダーの実装を優先する**
   - サーバー側の変更は軽い
   - 新しく作るクライアントから、このヘッダーに対応させる
   - 既存クライアントは、時間をかけて段階的に対応

3. **必要に応じて、クライアント側のバックオフ戦略を『ジッター化』する**
   - 待機時間に乱数を加える
   - 複数クライアントの再試行タイミングをずらす
   - これだけで、バックオフ競争の激しさが大きく低減することが多い

4. **レート制限の値を、実測データで決める**
   - 机上の計算ではなく、本番環境での動作を観察
   - ピーク時のリクエスト分布、再試行の実態を踏まえて調整

## まとめ

APIレート制限は、サーバー保護の有効な手段ですが、既存システムへの後付けは『クライアント側の再試行ロジック』との相互作用を無視できません。

設計段階で既存クライアントの実装を把握し、Retry-After ヘッダーの導入、段階的な値調整、ログによる監視を組み合わせることで、意図しない負荷増を防ぐことができます。

現場では、完璧な設計より「段階的に学びながら進める」ほうが、実は堅牢なシステムになることが多いものです。
