## 現場で起きやすい「キャッシュしたから安心」という誤解

Webアプリケーションのミドルウェア層で認証トークンを検証する際、パフォーマンス向上を目的にトークン検証結果をキャッシュするのは珍しくない実装です。毎回データベースやトークン発行サーバーに問い合わせるのは重いから、メモリやRedisに一度検証した結果を保持しておく──これ自体は理に適った最適化です。

しかし現場ではこうした場面に出くわします。

「権限を剥奪したユーザーが、なぜかまだ管理画面にアクセスできている」「セッション終了直後なのに、キャッシュされたトークンで古い権限のまま操作が通ってしまった」。

こうした問題の背景には、キャッシュの有効期限設定と、その無効化タイミングの判断が甘いケースが多くあります。今回は、実装段階で見落としやすいこの落とし穴を、検証を通じて整理します。

## 検証の前提：どこまでをキャッシュするか

まず整理が必要なのは、「トークン検証」という言葉が複数の処理を含んでいることです。

- **トークンの署名・有効期限検証**：トークン自体が改ざんされていないか、有効期限内か
- **トークンに紐づく権限情報の検証**：そのトークンの所有者がどんな権限を持っているか
- **セッションの有効性確認**：ユーザーがログアウトしていないか、セッションが無効化されていないか

一般的には、署名・有効期限検証はJWT形式なら署名だけで完結するため、キャッシュしなくても計算コストは低めです。問題になりやすいのは、**権限情報やセッション有効性をキャッシュする場合**です。ここに無効化タイミングの判断が入ります。

## 実装パターンと落とし穴の具体例

簡略化した実装例を見てみましょう。

```python
# 危険なパターン：権限情報をメモリキャッシュ、無効化なし
import time
from functools import lru_cache

token_cache = {}  # {token: (user_id, permissions, timestamp)}
CACHE_TTL = 3600  # 1時間

def verify_token_unsafe(token):
    if token in token_cache:
        user_id, permissions, cached_at = token_cache[token]
        # TTLだけで有効性判定
        if time.time() - cached_at < CACHE_TTL:
            return user_id, permissions
    
    # キャッシュなければDBから取得
    user_id, permissions = fetch_from_db(token)
    token_cache[token] = (user_id, permissions, time.time())
    return user_id, permissions
```

このコードの問題点：

1. **権限剥奪の反映遅延**：ユーザーの権限をDBで更新しても、キャッシュが残っている間は古い権限で通ります
2. **ログアウト後のアクセス許可**：セッション無効化フラグをDBに立てても、キャッシュには反映されません
3. **TTL固定の危険性**：全トークンが同じTTLで扱われるため、重要な権限変更がTTLの最後尾で起きると最大1時間反映されません

これらは「キャッシュの有効期限が切れるまで待つ」という受け身の設計になっており、**能動的な無効化がない**点が本質的な問題です。

## 検証環境と試験構成

実際に本番で起きる影響を測定するため、以下の構成で検証しました。

**環境：**
- Python Flask + Redis（キャッシュ層）
- PostgreSQL（権限情報の真実のソース）
- テスト用に複数のトークンを生成し、権限変更タイミングを制御

**試験シナリオ：**
1. ユーザーAが「管理者」権限でログイン、トークン取得
2. トークン検証時に権限情報をRedisに5分間キャッシュ
3. 30秒後、DBで権限を「一般ユーザー」に変更
4. 変更後、同じトークンで管理画面へのアクセスを試行

**期待値：** アクセス拒否（権限がない）

**実際の結果：** アクセス許可（キャッシュされた管理者権限で通る）

このズレが起きる時間幅は、キャッシュTTLに完全に依存します。5分キャッシュなら最大5分間、古い権限で動き続けます。

## 落とし穴を回避する設計判断

### 1. キャッシュの粒度を変える

権限情報全体をキャッシュするのではなく、**トークン自体の有効性だけキャッシュ**し、権限情報は毎回取得する案が考えられます。

```python
# 改善案：トークン有効性だけキャッシュ、権限は毎回取得
def verify_token_improved(token):
    # キャッシュ：トークンが「無効化されていないか」だけ
    if is_token_revoked_cached(token):
        raise AuthenticationError("Token revoked")
    
    # 権限情報は毎回DB取得（コスト低い）
    user_id, permissions = fetch_from_db(token)
    return user_id, permissions

def is_token_revoked_cached(token):
    # Redisに「無効トークンリスト」を保持
    # 存在しない＝有効、存在する＝無効
    return redis_client.exists(f"revoked:{token}")
```

この方式では、権限変更時にDBを更新するだけで、次のリクエストから新しい権限が反映されます。

### 2. キャッシュ無効化イベントを設計する

権限変更時に**能動的にキャッシュを削除**する仕組みを入れます。

```python
def revoke_user_permissions(user_id, new_permissions):
    # DBを更新
    update_user_in_db(user_id, new_permissions)
    
    # そのユーザーの全トークンをキャッシュから削除
    tokens = get_user_tokens(user_id)
    for token in tokens:
        redis_client.delete(f"auth_cache:{token}")
    
    # または、ユーザーIDベースで無効化タイムスタンプを記録
    redis_client.set(f"user_invalidated:{user_id}", time.time())
```

キャッシュ検証時に、このタイムスタンプと比較してキャッシュの鮮度を判定します。

### 3. TTLと無効化の二重構造

完全な無効化機構がない場合でも、**TTLを短くする**ことで影響範囲を限定できます。

```python
# シナリオ別のTTL設定
CACHE_TTL = {
    "read_only": 300,      # 読み取り専用なら5分でもOK
    "write_permission": 60,  # 書き込み権限は1分
    "admin": 10,           # 管理者権限は10秒
}
```

権限レベルが高いほどTTLを短くし、権限変更の影響を最小化します。

## 本番投入前に確認すべきポイント

1. **権限変更のフロー全体を追跡する**：権限をDBで変更してから、ミドルウェアで反映されるまでのラグを可視化してください。1秒か、5分か、それとも1時間か。

2. **キャッシュ削除の責任者を明確にする**：誰がいつ、どの条件でキャッシュを削除するのか。設計ドキュメントに明記してください。

3. **セッション無効化とトークン無効化の区別**：ログアウト時に何をどこまで無効化するのか。トークンそのものなのか、権限情報なのか。

4. **キャッシュレイヤーの障害を想定する**：Redisが落ちた場合、キャッシュ削除が失敗した場合の動作を決めておきます。デフォルトは「キャッシュなしで動作」にすべきです。

5. **監視・アラート設定**：キャッシュのヒット率、TTL切れのタイミング、権限変更から反映までのラグを測定できる仕組みを用意しましょう。

## 向いている案件、向かない案件

**キャッシュが有効な場合：**
- 権限情報が頻繁に変わらない業務システム
- トークン検証の頻度が非常に高い（秒間数千リクエスト）
- 権限変更に数秒～数分のラグが許容される

**キャッシュを避けるべき場合：**
- 権限の即時反映が必須（管理画面での権限剥奪後、即座にアクセス不可にしたい）
- ユーザーが頻繁にログイン・ログアウトする
- セキュリティインシデント対応で緊急に権限を剥奪する必要がある

小規模なシステムなら、キャッシュなしで素直にDB照会する方が、後々の保守負荷が低いケースも多いです。

## 結論：キャッシュは「最適化」であり「保険」ではない

トークン検証のキャッシュは、パフォーマンス最適化としては正当です。ただし、キャッシュを導入する際は、**その代償として権限反映のラグが生じることを明示的に受け入れる**必要があります。

「キャッシュしたから安心」ではなく、「キャッシュしたから、この期間は古い権限で動く可能性がある」という前提で、無効化戦略を設計してください。権限周りの実装は、一度本番で問題が出ると対応が難しい領域です。実装段階でこの判断を丁寧に詰めておくことが、後の運用を大きく楽にします。
