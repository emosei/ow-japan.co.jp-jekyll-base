## はじめに──本番環境で突然起きる「接続不可」の正体

Go で実装した API サーバーを本番環境に上げた直後、アクセス数が増えると「接続タイムアウト」や「connection refused」が散発的に発生するようになった。ところが、開発環境や負荷テスト環境では再現しない──こういった状況に直面したエンジニアは多いのではないでしょうか。

原因を調査してみると、データベースへのコネクションプールが枯渇していたことが判明するケースがあります。ただし厄介なのは、Go の標準ライブラリ `database/sql` のデフォルト設定では、この枯渇が **検出しにくい** という点です。負荷テストを実施したはずなのに、本番環境に上げて初めて問題が表面化する。その理由と、実装時の確認ポイントについて、実際の検証結果をもとに解説します。

## デフォルト設定の「最大接続数」が見落とされやすい理由

Go の `database/sql` パッケージでは、DB 接続プールの動作を制御するパラメータが複数あります。代表的なものは以下の通りです。

- `SetMaxOpenConns(n)` ── 最大オープン接続数
- `SetMaxIdleConns(n)` ── アイドル状態で保持する最大接続数
- `SetConnMaxLifetime(d)` ── 接続の最大生存時間

このうち、**デフォルトでは `SetMaxOpenConns` の値が「無制限」に設定されています**。つまり、制限がないように見えるため、多くの開発者はこのパラメータを明示的に設定しません。

しかし「無制限」という設定は、実は OS やデータベース側の制限に依存することを意味します。Linux の場合、プロセスあたりのファイルディスクリプタ数に上限があり、デフォルトでは 1024 程度に設定されていることが多いです。Go のコネクションプールはこの制限に達するまで接続を作成し続けるため、ある時点で突然「接続作成失敗」が起きるわけです。

```go
// デフォルト設定（危険）
db, err := sql.Open("postgres", dsn)
if err != nil {
    log.Fatal(err)
}
// SetMaxOpenConns を指定していない
// → OS のファイルディスクリプタ上限に依存する

// 推奨設定
db, err := sql.Open("postgres", dsn)
if err != nil {
    log.Fatal(err)
}
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(5 * time.Minute)
```

## 負荷テストで検出されない理由──テスト環境の「ぬるさ」

本題に入ります。負荷テストを実施したはずなのに、本番環境で初めて問題が発生する背景には、テスト環境と本番環境の差異があります。

### テスト環境で見落とされやすい条件

1. **テスト期間の短さ**  
   負荷テストは通常、数分から数十分程度の実行時間です。一方、本番環境では数時間、数日単位で稼働します。長時間稼働する中で、接続の作成と破棄が繰り返されると、OS レベルでのリソーク漏洩やタイムアウト待ちが蓄積されます。

2. **テスト環境の DB インスタンスが小規模**  
   開発環境や CI/CD 環境のデータベースは、リソースが限定されていることが多いです。本番環境の DB インスタンスが「最大接続数 500」に対し、テスト環境は「最大接続数 100」という設定になっていないか確認が必要です。

3. **ネットワーク遅延の差**  
   前回の記事でも触れましたが、テスト環境と本番環境のネットワーク遅延は異なります。遅延が大きいほど、接続がアイドル状態で保持される時間が長くなり、プール内の接続数が増加しやすくなります。

4. **同時接続数の粒度**  
   負荷テストツール（`ab`, `wrk`, `k6` など）で「100 並行接続」をシミュレートしても、実際には API サーバー内でさらに複数の DB 接続が生成される場合があります。1 つの HTTP リクエストが複数の DB クエリを実行すれば、コネクションプールの消費速度は想定より高くなります。

## 実装時の検証手順──枯渇を「見える化」する

では、どのように検証すればよいでしょうか。以下の手順を提案します。

### 1. 現在のプール状態をモニタリングする

Go の `database/sql` には `DB.Stats()` メソッドがあります。これでプール内の接続数をリアルタイムで確認できます。

```go
// プール状態の確認
ticker := time.NewTicker(1 * time.Second)
defer ticker.Stop()

go func() {
    for range ticker.C {
        stats := db.Stats()
        log.Printf("OpenConnections: %d, InUse: %d, Idle: %d, WaitCount: %d, WaitDuration: %v",
            stats.OpenConnections,
            stats.InUse,
            stats.Idle,
            stats.WaitCount,
            stats.WaitDuration,
        )
    }
}()
```

特に注目すべきは `WaitCount` と `WaitDuration` です。これらの値が増加している場合、接続の取得待ちが発生していることを意味します。

### 2. 本番環境の設定値を負荷テストに反映させる

テスト環境の設定を本番環境に合わせます。

```go
// 本番環境の制約を反映
db.SetMaxOpenConns(25)       // DB の max_connections の 5% 程度が目安
db.SetMaxIdleConns(5)        // OpenConns の 20% 程度
db.SetConnMaxLifetime(5 * time.Minute)
db.SetConnMaxIdleTime(2 * time.Minute)
```

### 3. 長時間の負荷テストを実施する

短時間ではなく、最低でも 30 分以上の負荷テストを実施し、`Stats()` の値が安定しているか確認します。

```bash
# 例：k6 での 30 分間の負荷テスト
k6 run --duration 30m --vus 50 load_test.js
```

## 実務投入時の追加確認ポイント

実装後、本番環境に投入する前に以下を確認してください。

- **データベース側の最大接続数設定を確認する**  
  API サーバーの `SetMaxOpenConns` がデータベースの `max_connections` を超えていないか。

- **ファイルディスクリプタ上限を確認する**  
  `ulimit -n` で OS の制限を確認し、必要に応じて引き上げる。

- **接続タイムアウト値を明示的に設定する**  
  `SetConnMaxLifetime` と `SetConnMaxIdleTime` を組み合わせ、不要な接続が蓄積しないようにする。

- **ログに接続エラーを記録する**  
  `sql.ErrConnDone` や `sql.ErrTxDone` が本番環境で発生していないか、ログから検証する。

- **複数の DB インスタンスがある場合、それぞれ設定を確認する**  
  マイクロサービス構成では、複数の DB への接続が並行して発生する場合があります。

## どんな案件で採用しやすいか

この検証は、以下のような案件で特に重要です。

- **高トラフィック・高並行性が予想される Web サービス**  
  予約システムやマーケットプレイスなど。

- **複数のデータベースに接続する構成**  
  マイクロサービスやポリグロット・パーシスタンス。

- **24 時間運用が必須のシステム**  
  長時間稼働による接続リソースの蓄積が起きやすい。

- **本番環境のリソースが限定されている場合**  
  クラウド上の小規模インスタンスや、共有ホスティング。

逆に、社内ツールや低トラフィックのシステムであれば、デフォルト設定でも問題が起きにくいかもしれません。ただし、成長を見据えるなら、最初から適切に設定しておく方が後々の手間を減らせます。

## まとめ

Go の `database/sql` はシンプルで扱いやすいライブラリですが、デフォルト設定の「無制限」という仕様が、かえって落とし穴になりやすいです。負荷テストで検出されない理由は、テスト環境の設定や期間が本番環境と異なることが多いためです。

実装時には `SetMaxOpenConns` を明示的に設定し、本番環境の制約を負荷テストに反映させ、長時間の検証を実施することが重要です。こうした一手間が、本番環境での突然の障害を防ぎます。
