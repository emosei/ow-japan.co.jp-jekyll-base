## 問題は「数が増えた時点」で顕在化する

小規模なシステムでは気にならないのですが、定期実行の処理が10個を超えたあたりから、現場で判断を迫られる場面が増えます。

ポーリング型の定期処理（CronJobやScheduledTask）が複数走るとき、実行タイミングが重なると何が起きるのか。単一サーバーであれば、OS側でプロセスをスケジューリングしてくれるので、ほぼ問題になりません。ところが分散環境、特に複数インスタンスで同じアプリケーションが動く場合は、全インスタンスが同じスケジュールで同じ処理を実行しようとします。

その結果：

- データベースの接続数が瞬間的に枯渇する
- ディスク I/O が集中してレスポンスが落ちる
- 外部API呼び出しのレート制限に引っかかる
- 処理間の排他制御がロック待ちで長時間ブロックされる

こうした問題は、本番環境で負荷が上がってから初めて気づくことが多いです。開発時点では「定期処理なんて軽いもの」という認識で進めてしまい、実装後に「なぜこんなに遅いのか」という相談を受けることになります。

## 「タイミング調整」と「実行保証」のトレードオフ

対策は大きく3つに分かれます。それぞれ異なるコストと制約を持っています。

### 1. 実行時刻をずらす（オフセット方式）

最もシンプルで、導入障壁が低い方法です。処理Aを毎時0分、処理Bを毎時5分、処理Cを毎時10分……という具合に、実行時刻を分散させます。

```
処理A: 0 * * * *       (毎時0分)
処理B: 5 * * * *       (毎時5分)
処理C: 10 * * * *      (毎時10分)
処理D: 15 * * * *      (毎時15分)
```

**メリット**
- 設定だけで実装できる
- 複雑なロジックが不要
- 各処理の実行時間を予測しやすい

**デメリット**
- 処理数が増えると、「どこにずらすか」の調整が煩雑になる
- 新しい定期処理を追加するたびに、既存の実行時刻を見直す必要が出る
- インスタンス数が増えたり、処理時間が変動すると、調整が無効になる

現場では、この方法で「何度も調整し直した」という経験があります。最初は上手くいっても、半年後に処理が1つ増えたら、また全体を見直す羽目になる。小規模チームでは、その見直しコストが意外と大きいのです。

### 2. リーダー選出（Leader Election）

複数インスタンスの中から「代表」を1つ決めて、その代表だけが定期処理を実行させる方法です。分散ロック（Redis、ZooKeeper、DynamoDB Conditional Writeなど）を使って実装します。

```python
# 疑似コード
def scheduled_task():
    lock_key = "task_leader_lock"
    ttl = 70  # 秒
    
    # ロック取得を試みる
    if redis.set(lock_key, instance_id, ex=ttl, nx=True):
        # このインスタンスが代表になった
        try:
            execute_actual_task()
        finally:
            redis.delete(lock_key)
    else:
        # 他のインスタンスが実行中。このインスタンスはスキップ
        pass
```

**メリット**
- インスタンス数が増えても、実行は1つだけに制限される
- タイミング調整の手間がない
- スケーリングに強い

**デメリット**
- ロック機構の導入と運用が必要
- ロック取得に失敗した場合の処理が実行されない（「実行されなかった」ことに気づきにくい）
- ロックサーバーが落ちると、定期処理が全く動かなくなる

実装時の注意点として、ロックのTTL（Time To Live）設定が重要です。処理の実行時間より短く設定すると、実行途中でロックが解放されて、別インスタンスが同じ処理を開始してしまいます。逆に長すぎると、インスタンスがクラッシュした時に、ロック解放を待つ間、他のインスタンスが待機し続けます。現場では、この「適切なTTL」を決めるのに議論が生じやすいです。

### 3. 分散キューイング（メッセージキュー経由）

定期処理を「キューに投入するだけ」にして、実際の処理実行はワーカーに任せる方法です。RabbitMQ、AWS SQS、Google Cloud Pub/Sub などを使います。

```python
# 定期処理: キューに投入するだけ（どのインスタンスでも実行OK）
def schedule_task_enqueue():
    queue.send_message(
        queue_name="process_queue",
        message_body={"task_type": "daily_report", "timestamp": now()}
    )

# ワーカー: キューから取得して実行（1メッセージは1ワーカーだけが処理）
def worker():
    while True:
        message = queue.receive_message()
        if message:
            execute_task(message)
            queue.delete_message(message)
```

**メリット**
- 処理の実行と投入を分離できる
- キュー機構が「重複実行防止」を担保する
- 処理が遅れても、キューに溜まるだけで、順序が保証される
- スケーリング時の調整が最小限

**デメリット**
- キューイングシステムの導入と保守が必須
- 「定期」という概念を、アプリケーション側で管理する必要がある
- キューの監視・アラートが複雑になる
- 小規模なシステムには「過剰」と感じられることが多い

## 実装時にハマりやすい落とし穴

### 「実行されたか」の確認が曖昧になる

特にリーダー選出方式で顕著ですが、ロック取得に失敗したインスタンスは、何もログを出さずにスキップしてしまいます。その結果、「定期処理が実行されていない」という問題に、数日後に気づくことになります。

対策としては、**ロック取得失敗時にも最小限のログを出す**ことが有効です。

```python
def scheduled_task():
    lock_key = "task_leader_lock"
    
    if redis.set(lock_key, instance_id, ex=70, nx=True):
        logger.info(f"Leader acquired. Executing task. instance={instance_id}")
        try:
            execute_actual_task()
        finally:
            redis.delete(lock_key)
    else:
        logger.debug(f"Leader lock not acquired. Skipping. instance={instance_id}")
```

さらに、定期的に「最後に実行されたのはいつか」をメトリクスとして記録しておくと、ダッシュボードで一目で確認できます。

### インスタンス再起動時の「重複実行」

ロック方式で、インスタンスがクラッシュしてロックが解放される前に再起動されると、新しいインスタンスが古いロックを上書きして、同じ処理を再度実行してしまう場合があります。

完全には防げませんが、**処理の冪等性（何度実行しても結果が同じ）を保証する**ことが現実的な対策です。

例えば、「日次レポート生成」なら、既存のレポートを上書きするのではなく、タイムスタンプ付きで新規作成するなど、設計段階で冪等性を組み込みます。

### スケジュール定義の「点検ミス」

処理数が増えると、Crontab や CloudWatch Events の設定が複雑になり、「このスケジュール、本当に意図通りか」という確認が難しくなります。

現場では、スケジュール設定をYAMLやJSONで一元管理し、デプロイ時に自動検証するアプローチが有効です。

```yaml
scheduled_tasks:
  - name: daily_report
    schedule: "0 2 * * *"
    timeout_seconds: 300
    leader_election: true
    
  - name: sync_external_data
    schedule: "*/15 * * * *"
    timeout_seconds: 60
    leader_election: true
```

## 小規模チームでの現実的な導入ステップ

1. **現状把握**: 既存の定期処理を全て洗い出し、実行時刻と処理時間を記録する
2. **衝突予測**: スプレッドシートで「同時実行される処理」を可視化する
3. **軽度な衝突なら**: オフセット方式で実行時刻をずらす（最も低コスト）
4. **衝突が頻繁なら**: リーダー選出方式を導入（中程度のコスト）
5. **複雑さが増したら**: メッセージキューへの移行を検討（高コスト、長期的な安定性）

重要なのは、「最初から完璧な仕組みを作る」のではなく、**現在の痛みに応じて段階的に対策する**ことです。10個の処理でオフセット方式が回っているなら、それは「正解」です。30個に増えて破綻したら、その時にリーダー選出方式への移行を検討する。そのくらいの柔軟性が、実務では重要です。

## まとめ

ポーリング型の定期処理は、シンプルで理解しやすいからこそ、「増えすぎてから対策する」という陥穽に落ちやすいです。分散環境での設計判断は、処理数やインスタンス数の「成長を予見する」ことから始まります。現在のシステム規模で充分な仕組みを選びながら、次の成長段階へのマイグレーションパスを頭の片隅に置いておく。その程度の先読みが、後々の手戻りを大きく減らします。
