## 金曜夜の「あ、やっぱり止まってた」が最も厄介な理由

メッセージキューやジョブキューを導入している組織なら、こういう場面に心当たりがあるはずです。

月曜朝、システム管理者が出社してログを確認したら、金曜の17時以降、外部サービスへの連携処理が全て失敗していた。再試行ロジックも働かず、数千件のデータが「どこにもいない状態」で放置されていた──という発見です。

原因を遡ると、キューの設定では「失敗したメッセージはデッドレターキューに移す」となっていたはずなのに、その死亡レターキュー自体の監視がなく、誰も気づかなかった。業務時間内なら数分で検知される問題が、夜間や休日に起きると数十時間そのままになります。

これは単なる「監視漏れ」ではなく、**死亡レターの扱いを『技術的な仕組み』と『運用の責任』で分断してしまった**ことが根本です。

## 死亡レターが「存在する」ことと「見える」ことは別問題

非同期キューシステムの多くは、デッドレターキュー（DLQ）の機能を持っています。一定回数失敗したメッセージをそこに移すという、見た目はシンプルな設計です。

しかし現場では、こんな判断が起きやすいです：

- **開発チーム**：「失敗時の処理は実装した。DLQに移される。あとは運用で見てもらう」
- **運用チーム**：「DLQという仕組みがあるなら、自動で何か対応されるんだろう」
- **実際**：誰も定期的に確認していない

DLQは「捨てるより前に一旦置いておく場所」に過ぎません。そこからどうするかは、明確に決めておかないと、単なる「問題の先送り」になります。

## 実装の甘さと運用の曖昧さが重なる地点

具体的には、こういう設計判断の漏れが起きています。

**1. 失敗の分類が不十分**

外部API連携で「失敗」と一括りにしていないでしょうか。例えば：

- `429 Too Many Requests`（レート制限）→ 数秒待ってリトライすれば成功する
- `400 Bad Request`（リクエスト形式が間違っている）→ コード修正が必要、リトライしても無駄
- `503 Service Unavailable`（相手サーバが落ちている）→ 相手の復旧を待つ必要がある

全て同じ再試行ロジックで扱うと、実は対応不可能な失敗までDLQに溜まります。

**2. DLQからの復旧手段が決まっていない**

DLQに入ったメッセージを「手動で確認して再投入する」のか、「自動で定期的に再試行する」のか、「外部ツールで別途処理する」のか。これが曖昧だと、DLQは単なる「忘却の場所」になります。

**3. 通知の責任が不明確**

DLQにメッセージが溜まっていることを誰が知るのか。メトリクス監視？ログ集約ツール？定期的な手動確認？業務時間外に通知する仕組みがないと、月曜朝の発見まで気づきません。

## 現実的な設計判断：三層の分け方

中小規模の組織が実装できる、比較的シンプルな構え方を示します。

### 第1層：即座に対応可能な失敗

```
失敗 → 指数バックオフで自動リトライ（数秒〜数分）
       → 成功したら終了
       → 失敗し続けたらDLQへ
```

レート制限や一時的なネットワークエラーはここで大半が解決します。

### 第2層：人間の判断が必要な失敗

```
DLQに到達したメッセージ
  → 失敗理由をログに記録
  → 失敗の種類を分類（形式エラー、権限エラー、一時的エラーなど）
  → 分類ごとに異なる処理を定義
```

例えば、形式エラーなら開発チームへの通知、一時的なサーバエラーなら翌日の再試行、という具合です。

### 第3層：監視と通知

```
DLQのメッセージ数が閾値を超えたら
  → 即座にアラート（メール、Slack、PagerDutyなど）
  → 営業時間外でも通知が届く仕組み
  → 定期レポート（日次または週次）で件数と分類を把握
```

ここが抜けると、業務時間外の問題は絶対に見逃されます。

## 実装と運用の責任分界を明文化する

技術的な仕組みだけでは不十分です。チーム間で「誰が何をするのか」を明確にしておく必要があります。

**開発チームの役割**
- リトライロジックの実装
- 失敗の分類とログ出力
- DLQからの復旧ロジックの実装（自動または手動の仕組み）

**運用チームの役割**
- DLQのメトリクス監視とアラート設定
- 定期的なDLQの確認と対応
- 復旧プロセスの実行

**両チームで合意すべき事項**
- 失敗の分類定義
- 各分類に対する対応方針
- DLQに溜まる許容件数と対応時間
- 業務時間外のエスカレーション経路

これを書面化しておくだけで、「あ、運用側が見ていなかった」という言い訳は減ります。

## 現実的に取れるアクション

すぐに全て完璧に設計するのは難しいので、段階的に進めるなら：

1. **まず現状把握**：今、DLQにどのくらいのメッセージが溜まっているか、何日分のログが残っているか確認する
2. **通知の仕組みを最初に入れる**：DLQの件数が増えたら通知が届く設定を優先。これだけで「気づかない」は解決します
3. **失敗の分類を段階的に追加**：全てを一度に完璧にするのではなく、最も多い失敗パターンから対応する
4. **復旧プロセスをドキュメント化**：手動対応でも構わないので、「何をするか」を明確にしておく

小さなチームほど「仕組みと運用が一体化していない」という問題が起きやすいです。DLQはあるが、その先がない──という状態は珍しくありません。

## 金曜夜の「あ、やっぱり」を減らすために

非同期キューは便利ですが、その便利さの代わりに「問題が見えにくくなる」という代償があります。DLQはその代償を少し緩和する仕組みですが、それ自体が新しい責任を生み出します。

技術的な正解よりも、「チーム内で責任を明確にしたか」「業務時間外でも検知できるか」という運用面の判断の方が、実は重要です。

月曜朝に「あ、やっぱり止まってた」と発見するのではなく、金曜の17時10分に「DLQにメッセージが溜まってますね」と通知が届く。その差は、設計の良し悪しではなく、運用の心構えの差です。
