## 現場で起きる「同じエラーが3回出ている」という報告

本番環境の障害対応をしていると、ログを見たときに「あれ、このエラーメッセージが何度も出ているな」という経験をします。同じリクエストIDで、同じエラー内容が3段階のミドルウェアに記録されているようなケースです。

これはバグではなく、むしろ一般的な実装パターンから自然に生まれる現象です。しかし、本来の原因を見極める際に、どのログを信頼するのか、どこまで遡るべきなのか、判断が曖昧になりやすい。特に複数チームで運用している場合、「どのレイヤーのエラーが真犯人か」で議論が分かれることもあります。

今回は、この多段エラーハンドリングの仕組みを検証し、ログノイズを減らしながら本来の原因を素早く特定する設計判断について、実装レベルで掘り下げます。

## ミドルウェアの独立したエラーハンドリングがなぜ多重記録を生むのか

### 層ごとの責任分離と記録の重複

一般的なWebアプリケーションでは、複数のミドルウェアが処理チェーンを形成します。例えば、Express.jsやRailsのような構成では以下のような層が存在します。

- **認証・認可ミドルウェア**：トークン検証、セッション確認
- **リクエスト検証ミドルウェア**：スキーマ検証、入力値チェック
- **ビジネスロジック層**：実際のデータ処理
- **エラーハンドリングミドルウェア**：最終的なエラーキャッチと応答

各層が「自分の責任範囲でエラーが起きたら記録する」という設計をすると、以下のような流れが起きます。

```
リクエスト到着
  ↓
認証ミドルウェア → エラー検出 → ログ記録 → throw
  ↓
グローバルエラーハンドラ → キャッチ → ログ記録 → レスポンス
```

認証ミドルウェアで既にエラーが記録されているのに、グローバルエラーハンドラが再度ログを出力します。さらに、リクエストログミドルウェアがレスポンスステータスを見て「4xxが返されている」と記録すれば、3段階の記録が発生するわけです。

現場では、これを「ログノイズ」と呼ぶことがあります。ただし、単に「ノイズだから削除しよう」とすると、本来必要な情報まで失われるリスクがあります。

## 検証環境での実装と観測

### 検証の前提条件

以下の条件で、Express.jsを使った簡易的なミドルウェアチェーンを構築し、エラーログの重複パターンを観測しました。

- Node.js 18系
- Express 4.18系
- 複数のミドルウェア層（認証、入力検証、エラーハンドリング）
- JSON形式のログ出力（タイムスタンプ、リクエストID、エラーレベル含む）

### サンプル実装

```javascript
// リクエストID付与ミドルウェア
app.use((req, res, next) => {
  req.id = `${Date.now()}-${Math.random()}`;
  next();
});

// 認証ミドルウェア（エラーを記録して throw）
app.use((req, res, next) => {
  const token = req.headers.authorization;
  if (!token) {
    console.log(JSON.stringify({
      timestamp: new Date().toISOString(),
      requestId: req.id,
      layer: 'auth-middleware',
      level: 'error',
      message: 'Missing authorization token'
    }));
    throw new Error('Missing authorization token');
  }
  next();
});

// 入力検証ミドルウェア
app.use((req, res, next) => {
  if (!req.body.userId) {
    console.log(JSON.stringify({
      timestamp: new Date().toISOString(),
      requestId: req.id,
      layer: 'validation-middleware',
      level: 'error',
      message: 'Missing userId in request body'
    }));
    throw new Error('Missing userId in request body');
  }
  next();
});

// グローバルエラーハンドラ
app.use((err, req, res, next) => {
  console.log(JSON.stringify({
    timestamp: new Date().toISOString(),
    requestId: req.id,
    layer: 'global-error-handler',
    level: 'error',
    message: err.message,
    stack: err.stack
  }));
  res.status(400).json({ error: err.message });
});
```

このコードを実行し、トークンなしでリクエストを送ると、認証ミドルウェアのログとグローバルエラーハンドラのログが両方出力されます。

### 観測結果

実際のログ出力：

```json
{"timestamp":"2026-06-15T10:23:45.123Z","requestId":"1718430225123-0.456","layer":"auth-middleware","level":"error","message":"Missing authorization token"}
{"timestamp":"2026-06-15T10:23:45.145Z","requestId":"1718430225123-0.456","layer":"global-error-handler","level":"error","message":"Missing authorization token","stack":"Error: Missing authorization token\n    at ..."}
```

**同じリクエストIDで、22ミリ秒の間に2つのエラーログが記録されています。**

さらに、リクエスト・レスポンスログミドルウェアを追加すると：

```json
{"timestamp":"2026-06-15T10:23:45.160Z","requestId":"1718430225123-0.456","layer":"request-log-middleware","level":"info","method":"POST","path":"/api/users","statusCode":400,"message":"Request completed with error"}
```

3段階の記録が生まれるわけです。

## ログノイズと本来の原因を見極める実装判断

### 層別の責任を明確にする

問題は「何を記録するか」ではなく、「どの層が最終的な責任を持つのか」を決めることです。

以下の設計パターンが実務では有効です。

**パターン1：エラーハンドリングの一元化**

各ミドルウェアはエラーを throw するだけで、ログ記録はグローバルハンドラに一任します。

```javascript
// 認証ミドルウェア（ログなし、throw のみ）
app.use((req, res, next) => {
  const token = req.headers.authorization;
  if (!token) {
    throw new Error('AUTH_MISSING_TOKEN');
  }
  next();
});

// グローバルハンドラが全責任を持つ
app.use((err, req, res, next) => {
  const errorCode = err.message;
  const context = {
    timestamp: new Date().toISOString(),
    requestId: req.id,
    errorCode: errorCode,
    path: req.path,
    method: req.method,
    userAgent: req.get('user-agent')
  };
  
  // ここで一度だけログ記録
  console.log(JSON.stringify({
    ...context,
    level: 'error',
    message: 'Request failed'
  }));
  
  res.status(getStatusCode(errorCode)).json({
    error: errorCode
  });
});
```

**メリット**：ログが一箇所に集約され、重複がない。原因追跡が単純。

**デメリット**：各ミドルウェアの詳細な動作ログが失われる。デバッグ時に困ることがある。

**パターン2：層別ログの役割分離**

各層が異なる情報を記録し、重複を避けます。

```javascript
// 認証ミドルウェア（詳細な認証ロジックのみ記録）
app.use((req, res, next) => {
  const token = req.headers.authorization;
  if (!token) {
    // 認証失敗の詳細を記録（エラーではなく info/debug レベル）
    console.log(JSON.stringify({
      timestamp: new Date().toISOString(),
      requestId: req.id,
      layer: 'auth-middleware',
      level: 'debug',
      message: 'Token validation failed',
      reason: 'missing_token'
    }));
    throw new Error('AUTH_MISSING_TOKEN');
  }
  next();
});

// グローバルハンドラ（ビジネス的な結果のみ記録）
app.use((err, req, res, next) => {
  const statusCode = getStatusCode(err.message);
  
  // エラーの場合のみ error レベルで記録
  if (statusCode >= 500) {
    console.log(JSON.stringify({
      timestamp: new Date().toISOString(),
      requestId: req.id,
      layer: 'error-handler',
      level: 'error',
      message: 'Internal server error',
      errorCode: err.message
    }));
  }
  
  res.status(statusCode).json({ error: err.message });
});
```

**メリット**：各層の情報が保持される。デバッグに有用。

**デメリット**：ログレベルの定義が複雑になる。チーム内で認識ズレが起きやすい。

## 実務投入時の追加確認ポイント

### ログ集約ツールとの相性

Datadog、New Relic、CloudWatch等のログ集約ツールを使っている場合、リクエストIDでフィルタリングして関連ログをまとめる機能があります。

この場合、多少の重複があっても、**同じリクエストIDのログをグループ化すれば、本来の流れが見える**ため、むしろ冗長性として機能します。

ただし、ログボリュームが増えると、インジェスト料金に影響するため、本番環境では以下を確認してください。

- 1日あたりのログ量増加率
- エラーログの割合
- ログ保持期間とコスト

### エラーコードの標準化

複数層でエラーが発生する場合、エラーコード（`AUTH_MISSING_TOKEN` など）を統一すると、ログ検索や集計が容易になります。

```javascript
const ERROR_CODES = {
  AUTH_MISSING_TOKEN: { status: 401, message: 'Authorization token is missing' },
  VALIDATION_FAILED: { status: 400, message: 'Request validation failed' },
  INTERNAL_ERROR: { status: 500, message: 'Internal server error' }
};
```
