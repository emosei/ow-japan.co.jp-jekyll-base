## 仕様変更は「一行の追加」ではなく「検証ツリーの拡大」である

スプリント中盤に仕様変更が入るとき、多くの人は「新しい要件を実装すればいい」と考えます。しかし現場では、それ以上に重い負荷が別の場所に発生しています。既存の実装判断と新しい仕様の間に「矛盾がないか」「データフローが破綻していないか」を検証する作業です。

この検証コストは、単純な足し算ではなく指数関数的に増えていきます。理由は、スプリント開始時に「ある前提」の下で実装判断が積み重ねられているからです。その前提が変わると、その上に立っているすべての判断を再評価する必要が生じるのです。

現場では、この再評価の必要性を見落とすか、軽く見積もりすぎることがほとんどです。結果として、検証漏れ、バグ、本番環境での不具合へと繋がっていきます。

## 「前提」の層構造と、仕様変更が引き起こす連鎖反応

具体的に考えてみましょう。スプリント開始時に、あなたのチームはこんな前提を決めていたはずです。

- **データモデルの前提**：ユーザーID、商品ID、取引日時の粒度と更新タイミング
- **ビジネスロジックの前提**：割引計算の順序、在庫確保のタイミング、キャンセル時の状態遷移
- **API仕様の前提**：リクエスト/レスポンスのスキーマ、エラーハンドリングの分岐
- **UI/UXの前提**：ユーザーが見るデータの鮮度、操作の順序制約、バリデーションのタイミング
- **パフォーマンスの前提**：キャッシュ戦略、クエリの最適化、同時接続数の想定

スプリント開始時、これらは互いに整合性を持つように設計されています。例えば、「割引は商品単価に対して適用する」という前提の下で、キャッシュ層の設計やAPIのレスポンス構造が決まっているわけです。

ここで、3日目に「割引は購入合計額に対して適用する」という変更が入ったとします。一見、計算ロジックの変更だけに見えます。しかし実際には、以下の再検証が必要になります。

```
1. ビジネスロジック層
   - 割引計算の順序を変更
   - 複数商品の組み合わせ時の動作を再定義
   - キャンセル時の部分払い戻しロジックを再検証

2. データベース設計
   - 既に保存されたデータで新ロジックが矛盾しないか
   - 過去データとの互換性を保つマイグレーション戦略

3. API仕様
   - レスポンスに「合計額」を含める必要があるか
   - 既存クライアントが新フィールドを無視できるか

4. キャッシュ戦略
   - 合計額ベースの割引は、ユーザーごと・セッションごとに異なる
   - 既存のキャッシュキーでは不十分か

5. UI表示ロジック
   - 商品追加時に割引額がリアルタイム更新される必要があるか
   - 既存のUIコンポーネントで対応できるか

6. テストケース
   - 既存のテストが新ロジックでも成立するか
   - 新しいエッジケースをどう検証するか
```

この検証ツリーが、仕様変更の「深さ」と「既存実装の複雑さ」に応じて、どんどん枝分かれしていくのです。

## 現場で見落とされやすい「整合性検証」のコスト

スプリント計画時に「仕様変更に対応する工数」を見積もるときは、通常、新機能の実装時間しか数えません。「割引計算ロジックを修正する：4時間」といった具合です。

しかし実際には、以下の検証作業が隠れています。

- **影響範囲の特定**：どのモジュール、どのテストケースが影響を受けるか
- **既存データとの互換性確認**：本番環境に既に存在するデータで矛盾が起きないか
- **クライアント側の対応確認**：Web、モバイル、API経由の複数クライアントで動作するか
- **段階的なデプロイ戦略**：新旧ロジックの並行運用が必要か、一括切り替えで大丈夫か
- **ロールバック計画**：問題が見つかった場合、どこまで戻すか

これらは「仕様変更を実装する」という一見単純なタスクの陰に隠れており、見積もり時点では見逃されやすいのです。

## 実装判断が「分岐」するメカニズム

さらに厄介なのは、スプリント中に複数の仕様変更が入る場合です。

1日目：「割引は商品単価ベース」で実装開始
3日目：「割引は合計額ベース」に変更
5日目：「割引は会員ランク別に異なる」という追加要件

こうなると、開発者ごと、機能ごとに「どの前提で実装すべきか」の判断が分岐します。結果として、同じ機能でも実装パターンが複数存在し、統合時に大量の矛盾が発見される、という現象が起きます。

これは「コード品質の問題」ではなく、**設計判断の基盤が動いている状態**なのです。

## 整合性検証コストを抑えるための実装観点

では、どうすればこの爆発的なコスト増加を抑えられるでしょうか。完全には防げませんが、設計段階で軽減できる工夫があります。

### 1. 「変更に強い」データモデルを最初に設計する

割引計算のように「変更される可能性が高い」ロジックは、ハードコーディングを避け、設定駆動型にしておくことが効果的です。

```json
{
  "discount_rules": [
    {
      "id": "rule_001",
      "type": "total_amount",
      "threshold": 10000,
      "discount_percent": 10,
      "valid_from": "2024-01-01",
      "valid_to": "2024-12-31"
    },
    {
      "id": "rule_002",
      "type": "member_rank",
      "rank": "gold",
      "discount_percent": 15
    }
  ]
}
```

こうしておくと、仕様変更時にコードを修正するのではなく、設定を追加・更新するだけで済みます。検証対象が「ルールエンジンの動作」に限定され、既存ロジックへの影響が最小化されます。

### 2. 「前提」を明示的にドキュメント化する

スプリント開始時に、設計判断の前提を明文化しておくことが重要です。

```
【割引計算の設計前提】
- 割引は商品単価に対して適用される
- 複数商品購入時は各商品の割引を合算
- キャンセル時は割引額も按分して返金

【この前提が変わる場合の影響範囲】
- ビジネスロジック：割引計算エンジン
- データベース：割引履歴テーブルのスキーマ
- API：商品詳細エンドポイントのレスポンス
- UI：商品追加時の割引表示ロジック
```

仕様変更が入ったとき、このドキュメントを参照することで、「何が変わったのか」「何を再検証する必要があるのか」が明確になります。

### 3. 統合テストの粒度を調整する

単体テストだけでは、仕様変更による整合性問題は見つかりません。スプリント中盤以降、仕様変更が入りやすい領域については、**統合テストを早期に組み込む**ことが効果的です。

- ユーザーの購入フロー全体をシミュレートするテスト
- 複数の割引ルールが同時に適用される場合のテスト
- キャンセル・返品時のデータ整合性テスト

これらを自動化しておくと、仕様変更後の回帰テストが格段に効率化されます。

## アジャイル開発での「仕様変更の受け入れ方」

アジャイル開発は「変更を歓迎する」という哲学を掲げています。それは正しい考え方です。しかし、その変更が既存実装にもたらすコストを軽視してはいけません。

むしろ、変更を受け入れるなら、その変更が既存実装にどう影響するかを、**受け入れ時点で評価する**ことが重要です。

実務的には、以下のような判断フローが有効です。

1. **変更内容を受け取ったら、すぐには実装しない**
2. **影響範囲を特定する**：「この変更は、どのモジュール、どのテストケースに影響するか」
3. **整合性検証に必要な工数を見積もる**：新機能の実装時間ではなく、既存実装の再検証に要する時間
4. **スプリント内で対応できるか判断する**：できなければ、次スプリントに繰り越すか、現在のスプリントの目標を調整するか
5. **変更を受け入れたら、その前提を明示的に記録する**

この判断プロセスを省略すると、スプリント終盤に「思っていたより大変だった」という事態が起きます。
