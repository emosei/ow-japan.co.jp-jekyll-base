## はじめに：現場で起きやすい認可情報の「ズレ」

Webアプリケーションの認証・認可処理をミドルウェアで一元管理する設計は珍しくありません。ただ、ここで厄介な問題が生じやすいのが、**セッション無効化後も古い認可情報がキャッシュに残り続ける**という現象です。

たとえば、ユーザーの権限が管理画面から剥奪されたのに、そのユーザーはしばらくの間、古い権限のまま機能を使い続けられてしまう。あるいは、ログアウト直後にブラウザのバックボタンで戻ると、実は権限がまだ有効だった──こういった状況は、セキュリティ監査で指摘されやすく、本番環境では予想外の対応コストを招きます。

この記事では、認証ミドルウェアのキャッシュ判定ロジックがどのような設計の甘さから問題を生むのか、実装検証を通じて整理します。

## ミドルウェアのキャッシュ判定が曖昧になる背景

認証ミドルウェアでキャッシュが導入される理由は明確です。毎リクエストごとにデータベースやトークンサーバーを叩いていては、パフォーマンスが落ちてしまうからです。

しかし、キャッシュの有効期限や無効化の条件が明示的に設計されていないと、以下のような判定が曖昧になりやすいのです。

- **キャッシュの有効期限**：セッションの有効期限とキャッシュの有効期限が別々に定義されていないか
- **無効化トリガー**：権限が変わったときに、どのタイミングでキャッシュをクリアするのか決まっていないか
- **複数サーバー間の同期**：ロードバランサー配下で複数インスタンスが動いているとき、一つのインスタンスでキャッシュをクリアしても他のインスタンスには反映されないのではないか

現場では、こうした設計の曖昧さが「いちおう動く」という理由で見過ごされやすく、セキュリティテストやセッション管理の監査で初めて指摘されることが多いです。

## 検証の前提と構成

今回の検証では、典型的な認証ミドルウェア実装を想定し、以下の条件で動作を確認しました。

**検証環境：**
- Express.js（Node.js）による簡易的なWebアプリケーション
- 認可情報をメモリキャッシュで保持するミドルウェア
- セッション情報はJWT（JSON Web Token）で管理
- 権限変更時の無効化ロジックを複数パターン実装

**比較対象：**
1. キャッシュ有効期限のみに依存するパターン
2. セッション有効期限とキャッシュ有効期限を独立させるパターン
3. セッション無効化時に明示的にキャッシュをクリアするパターン

## パターン1：キャッシュ有効期限に依存する実装

まず、最も単純（そして危険な）パターンを見てみます。

```javascript
const authMiddleware = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  
  if (!token) {
    return res.status(401).json({ error: 'No token' });
  }

  // キャッシュキーを作成
  const cacheKey = `auth:${token}`;
  
  // メモリキャッシュを確認
  if (cache.has(cacheKey)) {
    const cached = cache.get(cacheKey);
    // キャッシュの有効期限のみチェック
    if (cached.expiresAt > Date.now()) {
      req.user = cached.user;
      req.permissions = cached.permissions;
      return next();
    }
  }

  // キャッシュがなければトークンを検証してDBから権限を取得
  verifyToken(token).then(user => {
    const permissions = fetchUserPermissions(user.id);
    const cacheData = {
      user,
      permissions,
      expiresAt: Date.now() + 30 * 60 * 1000  // 30分
    };
    cache.set(cacheKey, cacheData);
    req.user = user;
    req.permissions = permissions;
    next();
  });
};
```

**問題点：**
- セッションが無効化されても、キャッシュの有効期限が切れるまで古い権限が生きたままになります
- 権限が剥奪されてから最大30分間、そのユーザーは古い権限で動作し続けます
- マルチインスタンス環境では、インスタンスAでセッション無効化が起きても、インスタンスBのキャッシュには反映されません

実際に検証してみると、セッション無効化後のリクエストでも認可チェックが通ってしまい、意図しない操作が可能になるケースが確認されました。

## パターン2：セッション有効期限とキャッシュ有効期限を分離する

次に、セッション自体の有効期限とキャッシュの有効期限を明確に分離する実装です。

```javascript
const authMiddleware = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  
  if (!token) {
    return res.status(401).json({ error: 'No token' });
  }

  const cacheKey = `auth:${token}`;
  
  // トークンを検証して、セッションの有効期限を確認
  verifyToken(token).then(decoded => {
    // セッションが無効化されていないか確認
    const sessionStatus = checkSessionValidity(decoded.sessionId);
    if (!sessionStatus.isValid) {
      cache.delete(cacheKey);  // キャッシュをクリア
      return res.status(401).json({ error: 'Session invalidated' });
    }

    // キャッシュをチェック（セッション有効期限より短い期限で設定）
    if (cache.has(cacheKey)) {
      const cached = cache.get(cacheKey);
      // キャッシュの有効期限とセッション有効期限の両方をチェック
      if (cached.expiresAt > Date.now() && 
          decoded.exp * 1000 > Date.now()) {
        req.user = cached.user;
        req.permissions = cached.permissions;
        return next();
      }
    }

    // キャッシュミスまたは期限切れ
    const permissions = fetchUserPermissions(decoded.userId);
    const cacheData = {
      user: decoded,
      permissions,
      expiresAt: Date.now() + 5 * 60 * 1000,  // 5分（セッション有効期限より短く）
      sessionId: decoded.sessionId
    };
    cache.set(cacheKey, cacheData);
    req.user = decoded;
    req.permissions = permissions;
    next();
  });
};
```

**改善点：**
- セッション無効化時に明示的にキャッシュをクリアしている
- キャッシュの有効期限をセッション有効期限より短く設定
- トークン検証のたびにセッション状態を確認

ただし、この実装にも課題があります。毎リクエスト時にセッション状態をDBから確認すると、パフォーマンスメリットが薄れてしまうのです。

## パターン3：明示的な無効化トリガーを組み込む

より実用的なのは、セッション無効化時に明示的にキャッシュをクリアするアプローチです。

```javascript
// キャッシュを管理するクラス
class AuthCache {
  constructor() {
    this.cache = new Map();
    this.sessionInvalidationQueue = new Set();
  }

  get(key) {
    return this.cache.get(key);
  }

  set(key, value) {
    this.cache.set(key, value);
  }

  // セッション無効化時に呼び出す
  invalidateSession(sessionId) {
    // 同じセッションIDを持つすべてのキャッシュを削除
    for (const [key, value] of this.cache.entries()) {
      if (value.sessionId === sessionId) {
        this.cache.delete(key);
      }
    }
    this.sessionInvalidationQueue.add(sessionId);
  }

  // 定期的に無効化キューをクリア（メモリリーク防止）
  cleanupInvalidationQueue() {
    this.sessionInvalidationQueue.clear();
  }
}

const authCache = new AuthCache();

// ログアウト時に呼び出す
app.post('/logout', (req, res) => {
  const sessionId = req.session.id;
  authCache.invalidateSession(sessionId);
  req.session.destroy();
  res.json({ success: true });
});

// 権限変更時に呼び出す
app.post('/admin/update-permission', (req, res) => {
  const userId = req.body.userId;
  // 該当ユーザーのすべてのセッションを無効化
  const sessions = findSessionsByUserId(userId);
  sessions.forEach(session => {
    authCache.invalidateSession(session.id);
  });
  // 権限をDBで更新
  updateUserPermissions(userId, req.body.permissions);
  res.json({ success: true });
});

// ミドルウェア内での使用
const authMiddleware = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  
  if (!token) {
    return res.status(401).json({ error: 'No token' });
  }

  const decoded = verifyToken(token);
  const cacheKey = `auth:${token}`;

  // キャッシュを確認
  if (authCache.get(cacheKey)) {
    const cached = authCache.get(cacheKey);
    if (cached.expiresAt > Date.now()) {
      req.user = cached.user;
      req.permissions = cached.permissions;
      return next();
    }
  }

  // キャッシュミス時
  const permissions = fetchUserPermissions(decoded.userId);
  const cacheData = {
    user: decoded,
    permissions,
    expiresAt: Date.now() + 15 * 60 * 1000,
    sessionId: decoded.sessionId
  };
  authCache.set(cacheKey, cacheData);
  req.user = decoded;
  req.permissions = permissions;
  next();
};
```

**利点：**
- セッション無効化時に即座にキャッシュが削除される
- 権限変更の影響が直ちに反映される
- 毎リクエスト時のDB
